# EvaCal: установка и обновление

Для пользователя основной путь — **готовые образы**, а не сборка Next.js на сервере.
Нужны Docker Engine с Compose **2.20+** (либо Docker Desktop), Bash, доступ к GHCR
и `curl` для загрузки конфигурации. Для самоподписанного TLS нужен `openssl`.
Node.js, Python, Git и исходники при установке готовой версии не требуются.
Установщик не устанавливает Docker и не запускает сторонние скрипты с правами root.

## Попробовать на своём компьютере

Скачайте установщик, просмотрите его и запустите:

```bash
curl -fL --retry 3 -o install.sh \
  https://raw.githubusercontent.com/onixus/EvaCal/main/deploy/install.sh
bash install.sh install --local
```

Откройте `http://localhost:8080`. Режим `--local` публикует порт **только на
127.0.0.1**, не требует сертификатов и не открывает приложение в локальную сеть.
На macOS запускайте без `sudo`; на Windows используйте терминал WSL2 с доступом
к Docker Desktop. На Linux пользователь должен иметь доступ к Docker daemon.

Секреты генерируются автоматически. Пароли начальных учёток выводятся после
миграции и сохраняются в `credentials.txt` с правами `600`. При первом входе
смените пароль, затем удалите этот файл. Для личной установки каталог —
`~/evacal`; для root — `/opt/evacal`. `--dir` меняет каталог.

## Сервер с HTTPS

```bash
bash install.sh install --dir /opt/evacal --domain evacal.example.org \
  --cert /etc/ssl/evacal/fullchain.pem --key /etc/ssl/evacal/privkey.pem
```

Нужны права записи в выбранный каталог. Без `--cert/--key` установщик создаёт
самоподписанный сертификат: браузер предупредит о недоверенном издателе.
По умолчанию серверный режим публикует 80/443 на всех IPv4-интерфейсах;
доступ ограничивайте сетевым экраном. Приватный ключ остаётся с правами `600`.
Нестандартные порты задаются через `--http-port` и `--https-port`.

Для внешнего reverse proxy, который завершает HTTPS:

```bash
bash install.sh install --no-tls --bind 127.0.0.1 --http-port 8080 \
  --domain evacal.example.org --secure-cookies
```

Прокси должен передавать корректные Host и forwarded-заголовки. Не используйте
`--secure-cookies` для прямого доступа по обычному HTTP. При смене собственного
TLS на HTTP установщик обновляет cookie-настройку, не оставляя старое `true`.

## Версия, база данных и несколько установок

`--version X.Y.Z` и `--version vX.Y.Z` выбирают один тег для **app и migrate**.
Используйте реально опубликованный тег. Без версии новая установка выбирает
`latest`. `update` без версии сохраняет ранее выбранный тег/канал.

При загрузке установщик проверяет совпадение OCI revision обоих образов,
фиксирует их полные digest и получает Compose/nginx-конфигурацию из того же
коммита. Несовпавшая пара не устанавливается. Для старых образов без revision
выдаётся предупреждение: проверить их соответствие автоматически невозможно;
обновлённый pipeline устраняет эту неопределённость для новых публикаций.

Встроенный PostgreSQL запускается отдельным наложением. Внешняя БД не запускает
лишний локальный PostgreSQL:

```bash
bash install.sh install --local \
  --database-url 'postgresql://evacal:URL_ENCODED_PASSWORD@db.example:5432/evacal'
```

Спецсимволы в пароле PostgreSQL кодируйте по правилам URI. Значения `.env`
не исполняются как shell-код; символы `$`, кавычки и обратные слеши сохраняются.
Управляющие команды изолируют Compose от посторонних экспортированных переменных
оболочки, включая `DATABASE_URL`.

Два независимых стенда требуют разных каталога, проекта и портов:

```bash
bash install.sh install --local --dir "$HOME/evacal-demo" \
  --project evacal-demo --http-port 8081
```

Имя проекта существующей установки менять нельзя: оно определяет её тома.
Для SQLite требуется сборка из исходников: `--sqlite --source /path/to/EvaCal`.
Смена СУБД — отдельный перенос данных, а не флаг для обновления.

## Сборка из исходников

```bash
git clone https://github.com/onixus/EvaCal.git
cd EvaCal
bash deploy/install.sh install --source --local
```

Собираются локальные образы app и migrate; они не подменяют локальные теги GHCR.
Выбранный клон запоминается. Перед обновлением сами получите и проверьте нужный
коммит, затем выполните `evacal update`. Установщик **не делает git pull/checkout**
и не переключает ветку пользователя. `--version` не является git checkout.
Корневой `docker-compose.yml` сохранён для существующего сценария разработки;
управляемая пользовательская установка использует файлы из `deploy/`.

## Управление

Копия менеджера — `<каталог>/evacal`; симлинк создаётся в `~/.local/bin` либо
`/usr/local/bin` при установке root, если имя свободно. Даже если каталог bin
не находится в PATH, работает полный путь:

```bash
~/evacal/evacal doctor
~/evacal/evacal status
~/evacal/evacal logs web
~/evacal/evacal update --version X.Y.Z
~/evacal/evacal backup
~/evacal/evacal restore ~/evacal/backups/evacal-ДАТА.tar.gz
~/evacal/evacal restart
~/evacal/evacal stop
```

`doctor` проверяет конфигурацию, показывает контейнеры и образы, не печатая `.env`.
Успех запуска означает готовность **app и nginx**, а не только процесса Node.js.
`passwords` сбрасывает пароли стендовых учёток после подтверждения.
`uninstall` оставляет данные; `uninstall --purge` удаляет также тома и каталог,
**включая backups**. Без интерактивного терминала опасные команды требуют
явного `--yes`. Общая очистка Docker-хоста и чужих образов не выполняется.

## Переход с установщика 0.6.0 и более ранних версий

`deploy/docker-compose.yml` сохранён как самостоятельный совместимый стек со
встроенным PostgreSQL. Старый `evacal update` скачивает только известные ему
файлы и не пересчитывает `COMPOSE_FILE`, поэтому удалять PostgreSQL из этого
файла нельзя. Его том и зависимости мигратора сохранены. Новый менеджер при
следующем обновлении переводит установку на `docker-compose.base.yml` плюс
нужные наложения, не меняя имя проекта или томов.

Чтобы уже первое обновление использовало staging, автоматический бэкап и
новые проверки, запускайте **новый менеджер отдельно**, не перезаписывая
работающий старый скрипт вручную:

```bash
# X.Y.Z замените на проверенный опубликованный релиз с новым менеджером.
curl -fL --retry 3 -o /tmp/evacal-upgrade.sh \
  https://raw.githubusercontent.com/onixus/EvaCal/vX.Y.Z/deploy/install.sh
bash /tmp/evacal-upgrade.sh update --dir /opt/evacal --version X.Y.Z
```

Просмотрите скачанный скрипт; используйте права владельца установки. Для
стенда в домашнем каталоге замените `--dir`. Старый менеджер не приобретает
новые гарантии безопасности внутри уже начатой команды обновления.

## Что происходит при обновлении

Сначала в закрытом временном каталоге загружаются оба образа и весь комплект
конфигурации, проверяются параметры, сертификаты и `docker compose config`.
Ошибка этой подготовки не меняет рабочую `.env` и не останавливает сервисы.

Затем `update` по умолчанию создаёт бэкап старой установки. Ошибка бэкапа
останавливает обновление. Пропуск — только явный `--skip-backup`, например после
согласованной внешней резервной копии. Предыдущая конфигурация сохраняется в
`.rollback.*`, приложение останавливается, миграции выполняются заново, затем
запускаются приложение и nginx. Проекты и имена томов сохраняются.
Между успешным бэкапом и миграциями писатели не возобновляются. При ошибке
бэкапа запускаются именно прежние контейнеры по ID, а не новое содержимое
изменяемого тега `:local`. Отдельная команда `backup` также не пересоздаёт app.

**Автоматического отката схемы БД нет.** После начала миграций ошибка требует
анализа логов и, при необходимости, восстановления бэкапа совместимой версией.
Возврат одного тега образа не отменяет миграцию. Копия `.rollback.*` содержит
конфигурацию, а не замену резервной копии данных.

## Данные и резервные копии

Тома: `pg-data` — PostgreSQL, `db-data` — SQLite, `storage-data` — локальные
артефакты. Данные SQLite теперь смонтированы в `/app/data`, **не в `/app/prisma`**:
старые файлы тома больше не закрывают миграции, схему и seed нового образа.
Старый стандартный SQLite URL автоматически переводится в `/app/data/dev.db`;
сам том не удаляется. Приложение работает как UID 1001, права writable-каталогов
готовит migrate, без рекурсивного chown всего приложения.

`backup` временно останавливает app/web, сохраняет PostgreSQL custom dump
(либо SQLite вместе с sidecar-файлами), локальное хранилище и `.env`, затем
возвращает ранее работающие сервисы. Имена томов определяются из контейнера,
поэтому поддерживаются отдельные проекты. Архив защищён правами `600` и
содержит секреты. Сертификаты сохраняйте отдельно. Других внешних писателей
в БД на время согласованной копии также необходимо остановить.

S3 в локальный архив **не входит**. Для S3 нужен согласованный снимок БД и
объектов отдельно; автоматический локальный backup в этом режиме отказывается
выдавать неполную копию за полную. Пользовательские bind-mount и нестандартные
пути хранения также требуют отдельной процедуры.

`restore` проверяет архив и СУБД, требует подтверждения, прекращает работу при
ошибках `pg_restore` и восстанавливает внешний PostgreSQL именно во внешнюю БД.
Текущая `.env` не перезаписывается архивной: проверьте соединение и секреты
перед восстановлением. Для PostgreSQL сервер должен быть запущен и доступен.
Старые SQLite-архивы с отдельным `dev.db` также поддерживаются.
До остановки сервисов SQLite-архив должен содержать ровно один непустой
обычный `dev.db`. Отдельный контейнер без сети и рабочих томов проверяет
формат, выполняет `integrity_check` и переносит завершённые записи WAL в
проверенную копию. Только эта копия устанавливается вместо действующей БД;
ошибка распаковки или проверки не удаляет исходные данные. На сервере не
требуются SQLite CLI или Node.js: используется Node 22 из образа migrate.
Для проверки нужен существующий контейнер migrate, даже завершённый.

Для внешнего PostgreSQL перед бэкапом/восстановлением выполняется проверка
соединения через `psql` до остановки app/web. Prisma-параметры `schema`,
`connection_limit`, `pool_timeout`, `pgbouncer`, `statement_cache_size`,
`socket_timeout` не передаются в libpq. Настройки TLS и кодированные данные
подключения сохраняются; неизвестные параметры не удаляются молча. URL
приложения в `.env` остаётся прежним. Дамп по-прежнему включает всю БД, не
только схему из Prisma URL. Иной сервер PostgreSQL может требовать совместимой
версии клиентских утилит; контейнер клиента по умолчанию использует версию 16.

## Комплект для распространения

Pipeline формирует `evacal-<tag>-deploy.tar.gz` и соседний `.sha256`. Архив
содержит менеджер, Compose, nginx, инструкцию и `RELEASE` с версией и коммитом,
но не исходники, секреты или данные. Получите **оба** файла из артефактов
успешной Jenkins-публикации (либо ручного workflow GitHub Actions):

```bash
sha256sum -c evacal-TAG-deploy.tar.gz.sha256   # macOS: shasum -a 256 -c ...
tar -xzf evacal-TAG-deploy.tar.gz
cd evacal-TAG-deploy
bash install.sh install --local
```

Версия берётся из `RELEASE`. При совпадении revision образов конфигурация
используется из архива, без загрузки raw GitHub. Это **не offline-комплект**:
образы всё ещё скачиваются из реестра. SHA256 обнаруживает повреждение файла,
но не заменяет доверенный канал получения или криптографическую подпись.

## Для сопровождающего: публикация

Основной путь остаётся ручной Jenkins `evacal-publish`. `SOURCE_URL` задаёт
репозиторий/локальное зеркало без привязки к пути конкретного Mac. Создайте
проверенный тег `vX.Y.Z`, выберите его в `REF`. `DRY_RUN=true` собирает оба
образа без login/push; для публикации снимите флаг. `MULTIARCH=true` собирает
linux/amd64 + linux/arm64, false — архитектуру текущего агента.

Общий `scripts/docker-publish.sh` сначала публикует app/migrate как кандидаты
`sha-<commit>`, запускает реальный Docker smoke-тест и только затем переводит
теги версии. Только стабильный `X.Y.Z` получает `latest`; prerelease и ветки
его не меняют. Зарезервированные имена `latest` и `sha-*` проверяются после
нормализации имени Git-ветки, включая замену `/` на `-`. Smoke проверяет штатный PostgreSQL, миграцию/повторный запуск,
UID приложения, запись артефактов, nginx HTTP и TLS с ключом 600 на нативной
архитектуре агента. Это не проверка всех архитектур и не нагрузочный тест.
При неуспехе кандидаты могут остаться в GHCR, но release/latest не продвигаются.

Ручной `.github/workflows/docker-publish.yml` использует тот же скрипт и тоже
публикует **оба** образа. Автоматические push/PR-триггеры не включены.
Архивы сохраняются как артефакты pipeline; GitHub Release сам не создаётся.
Для анонимной установки оба GHCR-пакета — `evacal` и `evacal-migrate` — должны
быть доступны на чтение. Публичность репозитория не заменяет настройку пакетов.

Регрессионные тесты: `npm run test:deploy` (либо `node --test deploy/tests/*.check.mjs`
без npm install). Тесты жизненного цикла используют имитацию Docker; отдельные
проверки `compose config` выполняются только при наличии Compose CLI.
Настоящий запуск образов — отдельный `scripts/smoke-docker.sh APP MIGRATE`.

### Проверка обновлений на Linux

Перед пересборкой или загрузкой образов менеджер временно закрепляет образ
существующего приложения для автоматического backup. Подготовка не останавливает
работающий сервис; временная ссылка удаляется при завершении, включая ошибки.
`update` выполняет backup до миграций. `--skip-backup` остаётся явным исключением.

Для HTTP-установки на `127.0.0.1` менеджер включает `EVACAL_LOCAL_HTTP`:
standalone за nginx может выдавать локальную session cookie без Secure.
Для TLS и внешнего bind этот режим выключен; `--secure-cookies` имеет приоритет.

Контрактные тесты запускаются отдельно: `npm run test:deploy` (Bash, GNU tar,
Docker Compose CLI). `npm run test:ci` запускает Vitest. Jenkins выполняет оба
набора в отдельных стадиях, поэтому ошибка установки не скрывает тесты приложения.
