# EvaCal — проект двух бизнес-фич (Horizon E)

Дата: 2026-09-14
База: `main` после #76 (PostgreSQL по умолчанию, S3-хранилище артефактов)

**Статус: реализовано.** E1 — PR #78, E2 — PR #79, E3 (добавлено по запросу после проектирования) — PR #80. Отличия реализации от проекта отмечены в разделе 4.

## 0. Зачем именно эти две

Платформа закрывает цепочку «опросник → расчёт → КП → комплект ГОСТ 34 → утверждение». Две вещи в этой цепочке до сих пор не измеряются, хотя данные для них почти все уже лежат в базе:

1. **Чем закончилась сделка и сколько на самом деле потратили.** Оценка утверждается, комплект выпускается, а дальше след обрывается. Калибровка (`lib/calibration.ts`) сравнивает формулу с утверждённой оценкой, но не с фактом. Рейтинг (`lib/leaderboard.ts`) считает объём и скорость, но не точность. Без факта и исхода компания не знает ни реальную маржу, ни цену скидки в вероятности выигрыша.
2. **Хватит ли людей на всё, что продано и продаётся.** У каждого расчёта есть Гант с ролями, часами и датами, но никто не складывает Ганты по портфелю. Перегруз инженеров на март виден только когда март наступил.

Отсюда две фичи: **E1 «Факт и исход сделки»** (замыкает цикл обучения) и **E2 «Ресурсный план по портфелю»** (замыкает цикл планирования). Они независимы, но E2 использует вероятность выигрыша, которую даёт E1.

Рассмотренные и отложенные альтернативы, чтобы к ним не возвращаться без причины:

| Кандидат                                 | Почему не сейчас                                                                     |
| :--------------------------------------- | :----------------------------------------------------------------------------------- |
| Лимиты скидок с цепочкой согласования КП | Нужен сначала факт исхода (E1), чтобы лимиты были обоснованы данными, а не интуицией |
| Версионируемые ставки ролей (rate cards) | Малая ценность, пока нет фактической маржи; делается в рамках E1, фаза 3             |
| Тендерный модуль 44-ФЗ/223-ФЗ            | Отдельный домен, большой; вернуться после E1/E2                                      |
| Импорт факта из Jira/YouTrack            | Это D2 из роадмапа; E1 закладывает под него поле и CSV-импорт                        |

## 1. E1 — Факт и исход сделки

### 1.1. Ценность

- **Пресейл** видит win rate по себе, по шаблону и по размеру скидки: «скидка 10% даёт +8 п.п. выигрыша, 20% — уже нет».
- **Архитектор/ГАП** видит, на каких этапах оценка систематически промахивается, по ролям и шаблонам.
- **Руководство** видит реальную маржу по выигранным проектам, а не плановую.
- **Калибровка** получает третий слой: формула → утверждено → факт. Сейчас она отвечает «насколько обычно уезжает оценка после архитектора»; станет отвечать «насколько уезжает от жизни».

### 1.2. Модель данных

Исход живёт на **проекте** (сделка одна, расчётов-версий несколько), факт по этапам — на **этапах утверждённого расчёта**.

```prisma
model Project {
  // ...существующие поля
  dealStatus     String    @default("open") // open | won | lost | cancelled
  dealClosedAt   DateTime?
  dealClosedBy   String?
  lossReason     String?   // price | competitor | timing | no_budget | scope | relationship | other
  lossComment    String?
  competitor     String?
  contractAmount Float?    // сумма договора без НДС в валюте расчёта
  contractCurrency String? // RUB | USD | ...
  wonCalculationId String? // версия расчёта, по которой подписан договор
  actualsClosedAt DateTime? // факт закрыт (проект сдан), после этого этапы не правятся

  @@index([dealStatus, dealClosedAt])
}

model Stage {
  // ...существующие поля
  actualHours     Float?    // null — факт не вносился
  actualStartDate DateTime?
  actualEndDate   DateTime?
  actualNote      String?   // «переделывали интеграцию из-за смены API»
}

model Calculation {
  // ...существующие поля
  actualPmHours   Float?    // факт РП, по аналогии с pmHours
}
```

Почему не отдельная таблица `StageActual`: факт у этапа один, история правок уже пишется в `AuditEvent` и `InternalChange`. Отдельная таблица нужна, когда факт приходит из внешней системы по дням; это фаза 3 (импорт).

Правила:

- `dealStatus` меняется только у проекта, у которого есть хотя бы один `approved` расчёт (нечего выигрывать).
- `won` требует `wonCalculationId` из своих расчётов; `contractAmount` необязателен, но без него маржа не считается и в дашборде проект помечается «без суммы».
- `lost` требует `lossReason`.
- Факт вносится только по этапам `wonCalculationId`; после `actualsClosedAt` — только через админа (аудит).
- Переоткрыть сделку можно (`won → open`), с записью в аудит.

### 1.3. Метрики (чистая логика, `lib/actuals.ts`)

Все функции без Prisma, на входных строках, как в `lib/calibration.ts`.

- **Точность этапа** `accuracy = actualHours / approvedHours` (null, если нет факта). Отклонение `deviation = accuracy - 1`.
- **Точность расчёта** — то же по сумме этапов с фактом; этапы без факта в знаменатель не входят, и это явно показывается («факт внесён по 7 из 9 этапов»).
- **Фактическая маржа** `(contractAmount − actualCost) / contractAmount`, где `actualCost = Σ actualHours × roleRate × (1 + overhead)`; ставки берутся из расчёта (`roleRates` или `DEFAULT_ROLE_RATES`).
- **Win rate** = won / (won + lost) за период; `cancelled` не считается проигрышем и показывается отдельно.
- **Скидка и исход**: бакеты скидки 0 / 1–5 / 6–10 / 11–20 / 20+, по каждому win rate и число сделок. При < 5 сделок в бакете значение помечается «мало данных».
- **Систематическое смещение по роли**: медиана `deviation` по всем этапам роли за период; знак говорит «недооцениваем / переоцениваем».

Калибровка (`lib/calibration.ts`) получает опциональный третий коэффициент `approved→actual` по тем же соседям и показывает его рядом с текущим, если у соседа есть факт.

| :------ | :-------------------------------------------- | :--------------- | :------------------------------------------------------------------------------------------------ |

| `PATCH` | `/api/calculations/:id/stages/:stageId`       | architect, admin | Существующий маршрут, добавляются `actualHours`, `actualStartDate`, `actualEndDate`, `actualNote` |
| `PATCH` | `/api/calculations/:id`                       | architect, admin | Добавляется `actualPmHours`                                                                       |

| `POST`  | `/api/calculations/:id/actuals/import`        | architect, admin | CSV `stage;hours[;start;end]`, сопоставление по имени этапа с отчётом о несовпадениях (фаза 3)    |

### 1.5. UI

- **Карточка проекта** (`/projects/:id`): блок «Сделка» со статусом, кнопки «Выиграно / Проиграно / Отменено», модальное окно с причиной, суммой и выбором версии. После `won` — прогресс «факт внесён по N из M этапов» и ссылка на расчёт.
- **Расчёт архитектора** (`ArchitectEditor`, `StageTable`): колонка «Факт, ч» и даты факта, видна только у `wonCalculationId`; строка итогов показывает `accuracy` цветом (±10% зелёный, ±25% жёлтый, дальше красный). Кнопка «Закрыть факт».
- **Панель калибровки** (`CalibrationPanel`): третий столбец «факт», если есть у соседей.
- **Новая страница `/analytics`** (staff): две вкладки, «Сделки» и «Точность оценок». Графики: win rate по месяцам, причины проигрышей, скидка/исход, scatter «утверждено vs факт» по расчётам, медианное смещение по ролям.
- **Рейтинг `/leaderboard`**: у архитекторов добавляется «точность» (медианное |deviation| по закрытым проектам), у пресейлов — win rate. Открытая страница, поэтому суммы не показываются, как и сейчас.

### 1.6. Тесты

- `lib/__tests__/actuals.test.ts`: точность с частичным фактом, маржа с оверхедом и без суммы, бакеты скидки с порогом «мало данных», смещение по роли, переходы статусов сделки (недопустимые комбинации).
- Маршруты: `won` без утверждённого расчёта → 409; факт по не выигранной версии → 409; факт после закрытия → 403 для архитектора, 200 для админа с аудитом.
- E2E: продолжение «Северного банка» — выиграть сделку, внести факт по двум этапам, увидеть точность на карточке.

### 1.7. Фазы

1. Модель, PATCH-маршруты, блок «Сделка» и колонка «Факт» (1 PR).
2. `/analytics` и правки калибровки и рейтинга (1 PR).

## 2. E2 — Ресурсный план по портфелю

### 2.1. Ценность

- **ГАП/PMO** видит загрузку ролей по неделям на 3–6 месяцев вперёд по всем проектам: что продано (won), что утверждено, что в воронке с вероятностью.
- **Архитектор** при правке дат в Ганте сразу видит, что сдвигает инженеров в перегруженную неделю.
- **Руководство** получает аргумент к найму: «с апреля аналитиков не хватает на 1,5 ставки при текущей воронке».

### 2.2. Модель данных

```prisma
// Ёмкость ролей. Одна строка — одна роль с датой начала действия;
// история хранится, чтобы прошлые недели не пересчитывались задним числом.
model RoleCapacity {
  id            String   @id @default(cuid())
  role          String   // canonical Role из lib/roles.ts
  headcount     Float    // ставок (1.5 = полтора человека)
  hoursPerWeek  Float    @default(30) // продуктивных часов на ставку; 30 = 6 ч × 5 дней, как в DEFAULT_SCHEDULE_CONFIG
  effectiveFrom DateTime
  note          String?
  createdBy     String
  createdAt     DateTime @default(now())

  @@index([role, effectiveFrom])
}
```

Спрос отдельно не хранится: он считается из `Stage` (role, hours, startDate, endDate) на лету. Это единственный источник правды, и он уже есть.

### 2.3. Логика (чистая, `lib/capacity.ts`)

- **Распределение этапа по неделям**: часы этапа раскладываются равномерно по рабочим дням между `startDate` и `endDate` (с учётом `includeWeekends` расчёта), затем суммируются по ISO-неделям. Этапы `isApprovalTask` и роль `customer` не создают спроса.
- **Вес расчёта** (вероятность, что работа состоится):

  | Состояние                                |                                                   Вес |
  | :--------------------------------------- | ----------------------------------------------------: |
  | проект `won` (E1)                        |                                                   1.0 |
  | расчёт `approved`, сделка `open`         |                                                   0.6 |
  | `pending_approval`                       |                                                   0.3 |
  | `draft`                                  | 0 (не считается, можно включить фильтром с весом 0.1) |
  | проект `lost` / `cancelled` / `archived` |                                                     0 |

  Веса — константы в одном месте, позже заменяются на win rate по бакету скидки из E1.

- По проекту берётся **одна версия**: `wonCalculationId`, иначе последняя `approved`, иначе последняя `pending_approval`. Черновики не суммируются с утверждёнными версиями того же проекта.
- **Загрузка** `utilisation = demand / capacity` по ячейке (роль × неделя). Ёмкость — активная строка `RoleCapacity` на понедельник недели; если строки нет, ёмкость неизвестна и ячейка показывает только спрос в часах.
- **Сигналы**: ячейка > 100% — перегруз, > 85% — предел, < 40% при наличии ёмкости — простой. Считаются два ряда: «только won+approved» (твёрдый) и «с воронкой» (взвешенный).
- **What-if**: функция принимает список правок `{ calculationId, startDateShiftDays }` и пересчитывает без записи в базу; страница дёргает её при перетаскивании.

### 2.4. API

| Метод             | Путь                                                  | Роль                       | Что делает                                                                                       |
| :---------------- | :---------------------------------------------------- | :------------------------- | :----------------------------------------------------------------------------------------------- |
| `GET`             | `/api/capacity?from=&to=&scope=firm\|weighted&roles=` | architect, reviewer, admin | Матрица роль × неделя: спрос (твёрдый и взвешенный), ёмкость, загрузка, список расчётов в ячейке |
| `POST`            | `/api/capacity/what-if`                               | architect, admin           | Та же матрица с временными сдвигами расчётов                                                     |

| `GET`             | `/api/calculations/:id/capacity-warnings`             | architect, admin           | Недели, где этот расчёт делает роль перегруженной                                                |
| `GET`             | `/api/capacity/xlsx`                                  | architect, admin           | Выгрузка матрицы (через `lib/xlsx.ts`, с защитой от formula injection)                           |

### 2.5. UI

- **Новая страница `/capacity`** (architect, reviewer, admin): тепловая карта роль × неделя, переключатель «твёрдый / с воронкой», горизонт 13 или 26 недель, фильтр ролей. Клик по ячейке — список расчётов с часами и ссылками. Перетаскивание проекта по горизонтали — what-if, с кнопкой «применить» (меняет `startDate` расчёта через существующий PATCH и пересчитывает Гант).
- **Гант архитектора** (`GanttChart`): полоса предупреждений над диаграммой «Инженер: 135% на нед. 12–14», по данным `capacity-warnings`. Появляется при сохранении дат.
- **Админка** (`/admin`): вкладка «Ёмкость ролей» с таблицей и датой начала действия.
- **Главная архитектора** (`/architect`): виджет «ближайшие 4 недели» с тремя худшими ролями.

### 2.6. Тесты

- `lib/__tests__/capacity.test.ts`: разложение этапа через выходные и границу недели, вес по статусам, выбор одной версии на проект, ёмкость по `effectiveFrom` (до первой строки — неизвестна), пороги сигналов, what-if не мутирует вход.

- E2E: после утверждения расчёта «Северного банка» на `/capacity` появляется его спрос.

## 3. Общие решения

- **Миграции**: обе фичи добавляют только nullable-поля и одну таблицу; миграция PostgreSQL через `npm run db:migrate:pg`, SQLite — `db push`.
- **Права**: ничего нового в ролях; используются существующие `requireStaff`/`requireRole`. Гости по share-ссылке ни исход, ни факт, ни загрузку не видят.
- **Аудит**: все записи исхода и факта — в `AuditEvent`, как и утверждения.
- **Производительность**: `/api/capacity` читает этапы только активных проектов за диапазон дат (индекс `Stage(calculationId, order)` дополняется `Stage(startDate)`); на портфеле в 200 расчётов это одна выборка.
- **Порядок**: E1 фаза 1 → E2 фаза 1 → E1 фаза 2 → E2 фазы 2–3 → E1 фаза 3. Так раньше всего появляется поток данных (факт и исход), на котором потом настраиваются веса E2.

## 4. Что вышло иначе и что добавилось

### 4.1. Отличия реализации E1 и E2 от проекта

- Исход сделки может закрыть не только пресейл, но и архитектор с админом: раздел `/projects` в UI открыт только им, и без этого кнопки некому было бы нажимать. API принимает все три роли.
- Точность в рейтинге добавлена как отдельная колонка, формула оценки не менялась: иначе баллы всех архитекторов сдвинулись бы в день выкладки без изменения их работы.
- Веса воронки в E2 оставлены константами (`WEIGHTS` в `lib/capacity.ts`): win rate по бакету скидки станет основой, когда наберётся не меньше пяти решённых сделок на бакет.
- What-if реализован кнопками «на неделю раньше / позже» в списке расчётов ячейки, а не перетаскиванием: в тепловой карте роль × неделя нет строки проекта, которую можно тянуть.
- CSV-импорт факта (E1 фаза 3) сделан с dry-run: сначала отчёт о несовпавших этапах, потом запись.

### 4.2. E3 — контроль сроков, отклонения по задачам, конструктор срезов

Запрошено после реализации E1 и E2. Использует уже собранный факт.

**Контроль сроков** (`lib/schedule.ts`). У этапов выигранной версии вводятся даты факта. Статус этапа: план, в работе (есть старт), просрочен (плановое окончание прошло, факта окончания нет), завершён. Сдвиг окончания = факт − план, дней. Прогноз окончания проекта = плановое окончание + текущий сдвиг, где текущий сдвиг — максимум из сдвигов завершённых этапов и просрочек незавершённых. Статус проекта: не начат, в графике, риск срыва (сдвиг 1–5 дней), опоздание (больше 5), завершён. Показывается на карточке проекта и в панели факта.

**Отклонения по одинаковым задачам** (`lib/deviations.ts`). Имя этапа приводится к ключу без регистра, лишних пробелов и номера в начале, поэтому «1. Установка агентов» и «установка агентов» — одна задача. Сравнивается отношение факт / план − 1, а не абсолют: норматив вида «5 минут на агент» не зависит от объёма, и перерасход виден как доля. По задаче считается медиана по всем выигранным проектам; график на вкладке `/analytics?tab=deviations` диверджентный (перерасход вправо, недорасход влево, допуск серым), цвета проверены валидатором для светлой и тёмной темы.

**Конструктор срезов** `/analytics/deviations`. Выбор задач, фильтры (роль, шаблон, архитектор, заказчик, период исхода), группировка (задача, роль, шаблон, архитектор, заказчик, месяц, расчёт), метрика (медиана, среднее, P90), часы или календарные дни, допуск, порог «мало данных». Срезы сохраняются в `DeviationReport` (общие; удаляет автор или админ), выгружаются в xlsx. API: `/api/deviations/tasks`, `/api/deviations/report`, `/api/deviations/report/xlsx`, `/api/deviations/reports`.
