# Миграция проектов ГОСТ 34 и регрессионный контроль (EvaCal v0.3.0)

Документ описывает нормативную привязку проектов, механизмы миграции ранее выпущенных комплектов на актуальный стандарт ГОСТ 34.602-2020, фиксацию релизных снимков и комплексную систему регрессионных тестов (57 тестовых сьютов, 487 тестов).

---

## 1. Нормативная привязка проекта и комплектов

Каждый расчёт (`Calculation`) и каждый выпущенный комплект документов (`GostPackage`) фиксируют, каким нормативным профилем и какой версией генератора они сформированы:

| Поле                     | Смысл                                                           | Где хранится                                 |
| ------------------------ | --------------------------------------------------------------- | -------------------------------------------- |
| `standardProfileId`      | Идентификатор профиля (`ru-gost34-current`, `gost34-legacy-89`) | Таблица `Calculation`, метаданные `GostPackage` |
| `standardProfileVersion` | Редакция профиля на момент выпуска (`2020`, `1989`)             | Таблица `Calculation`, метаданные `GostPackage` |
| `generatorVersion`       | Версия генератора документов (`GOST34_GENERATOR_VERSION`)       | Таблица `Calculation`, `snapshotData`        |
| `generatedAt`            | Временная метка выпуска комплекта                               | Таблица `Calculation`, `GostPackage`         |
| `snapshotData`           | Полный неизменяемый JSON-снимок проекта и структуры ТЗ          | Таблица `GostPackage` (`artifactStorage.ts`)  |

> [!NOTE]
> **Обратная совместимость:** пустая привязка — признак проекта, созданного до внедрения реестра профилей. Такой проект автоматически считывается как `gost34-legacy-89@1989` с флагом `inferred: true`, исключая случайную подмену нормативной базы.

Чтение и управление привязкой сосредоточено в [`lib/gost34/migration/binding.ts`](../lib/gost34/migration/binding.ts):
```ts
resolveProjectBinding(calculation); // → ProjectStandardBinding
buildBindingUpdate(profileId);      // → поля для prisma.calculation.update
```

Привязка записывается автоматически при каждом успешном экспорте комплекта документов (`app/api/calculations/[id]/gost34/route.ts`). При выпуске релиза формируется снимок через [`lib/gost34/snapshotPersistence.ts`](../lib/gost34/snapshotPersistence.ts), гарантирующий воспроизводимость артефактов в архиве.

## 2. Процедура миграции на ГОСТ 34.602-2020

### Порядок действий в интерфейсе

1. В Студии ГОСТ 34 открыть шаг **«Нормативный профиль»** → панель **«Нормативная привязка проекта»**.
2. Изучить сводный дифф изменений: сопоставление разделов, новые подразделы, устаревшие термины и ссылки на нормативы.
3. Нажать кнопку **«Мигрировать на ГОСТ 34.602-2020»** — привязка расчёта обновляется, а разделы ТЗ перестраиваются под новую схему.

> [!IMPORTANT]
> Миграция никогда не выполняется неявно при фоновом открытии проекта. Смена стандарта влечёт изменение структуры ТЗ и является осознанным решением архитектора.

### REST API миграции

| Метод  | Маршрут                                  | Действие                                                        |
| ------ | ---------------------------------------- | --------------------------------------------------------------- |
| `GET`  | `/api/calculations/:id/gost34/migration` | Предпросмотр диффа миграции без записи в БД                     |
| `POST` | `/api/calculations/:id/gost34/migration` | Применение миграции: обновляет профиль и трансформирует разделы |

Параметр `docType` (по умолчанию `TZ`) задаёт тип документа для сравнения. Запрос `POST` принимает целевой `targetProfileId`. Назначение профилей в статусе `preview` блокируется с кодом 400.

### Анализ различий (`buildMigrationDiff`)

Функция `buildMigrationDiff()` компилирует модель документа дважды — в исходном и целевом профилях — и формирует подробный отчёт:
- **Структурные различия:** добавленные разделы, исключённые пункты, изменение иерархии нумерации;
- **Снятые legacy-ссылки:** ссылки на отменённые стандарты (`ГОСТ 34.602-89 → ГОСТ 34.602-2020`, ссылки на РД 50);
- **Требования:** появление новых обязательных требований и упразднение неактуальных кодов;
- **Валидация и конфликты:** замечания валидатора уровней `ERROR` и `WARNING`;
- **Статусы применимости нормативов:** пункты, оставшиеся в статусе `NOT_APPLICABLE` или `UNKNOWN`;
- **Состояние черновиков LLM:** сопоставление принятых черновиков узлов (`GostDraftNode`) со структурой целевого стандарта.

Флаг `requiresAttention: true` информирует архитектора о наличии моментов, требующих ручной доработки перед финальным согласованием.

## 3. Контрольные эталоны (Golden Documents)

Для гарантии стабильности генерации в каталоге [`lib/gost34/__tests__/golden/`](../lib/gost34/__tests__/golden/) хранятся 9 типовых отраслевых сценариев:

1. `generic-corporate-as` — типовая корпоративная автоматизированная система;
2. `ispdn` — система обработки персональных данных (152-ФЗ);
3. `kii` — значимый объект критической информационной инфраструктуры (187-ФЗ, Приказ ФСТЭК № 239);
4. `bank` — автоматизированная банковская система (положения Банка России 683-П, 757-П);
5. `nfo` — некредитная финансовая организация;
6. `air-gapped-as` — изолированный контур без выхода в Интернет;
7. `high-availability-as` — отказоустойчивый кластер повышенной доступности (Active-Active);
8. `simple-internal-system` — внутренняя легковесная утилита;
9. `legacy-gost34-602-89` — проект в прежней нормативной редакции 1989 года.

Каждому сценарию соответствует эталонный снимок `<id>.json`, содержащий:
- иерархию разделов с числом параграфов и заголовками таблиц;
- нормативные коды требований;
- матрицу трассируемости и покрытие трудозатрат;
- карту применимости нормативов;
- контрольные метрики валидации.

Обновление эталонов при сознательном изменении алгоритмов генерации:
```bash
npm run test:golden:update
```
