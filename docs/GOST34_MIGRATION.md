# Миграция проектов ГОСТ 34 и регрессионный контроль

Документ описывает то, что закрывает PR-12 плана модернизации: нормативную
привязку проекта, миграцию ранее выпущенных комплектов на ГОСТ 34.602-2020 и
набор регрессионных тестов, которым эта миграция удерживается.

---

## 1. Нормативная привязка проекта

Расчёт (`Calculation`) хранит, каким профилем и какой версией генератора
выпускался комплект документов:

| Поле                     | Смысл                                                           |
| ------------------------ | --------------------------------------------------------------- |
| `standardProfileId`      | Идентификатор профиля (`ru-gost34-current`, `gost34-legacy-89`) |
| `standardProfileVersion` | Редакция профиля на момент выпуска (`2020`, `1989`)             |
| `generatorVersion`       | Версия генератора документов (`GOST34_GENERATOR_VERSION`)       |
| `generatedAt`            | Время последнего выпуска комплекта                              |

Поля опциональные. **Пустая привязка — это не ошибка, а признак проекта,
выпущенного до реестра профилей**: такой проект читается как
`gost34-legacy-89@1989`, а сама привязка помечается флагом `inferred`, чтобы
выведенное значение нельзя было спутать с сохранённым.

Чтение и запись привязки — `lib/gost34/migration/binding.ts`:

```ts
resolveProjectBinding(calculation); // → ProjectStandardBinding
buildBindingUpdate(profileId); // → поля для prisma.calculation.update
```

Привязка записывается автоматически при каждом успешном экспорте документа или
комплекта (`app/api/calculations/[id]/gost34/route.ts`). Сбой записи логируется,
но не ломает уже сформированный файл.

После обновления кода схему БД нужно синхронизировать:

```bash
npm run db:push
```

## 2. Миграция на ГОСТ 34.602-2020

### Порядок

1. Мастер выпуска → шаг «Профиль» → панель «Нормативная привязка проекта».
2. Панель показывает diff **до** записи: что появится, что уйдёт, что осталось.
3. Кнопка «Мигрировать на ГОСТ 34.602-2020» меняет привязку расчёта.

Никакой автоматической миграции при открытии проекта не происходит: смена
редакции — решение пользователя, а не побочный эффект.

### API

| Метод  | Маршрут                                  | Действие                           |
| ------ | ---------------------------------------- | ---------------------------------- |
| `GET`  | `/api/calculations/:id/gost34/migration` | Предпросмотр diff, ничего не пишет |
| `POST` | `/api/calculations/:id/gost34/migration` | Применение: обновляет привязку     |

Параметр `docType` (по умолчанию `TZ`) выбирает документ, по которому строится
diff. `POST` принимает `targetProfileId`; профиль со статусом `preview` назначить
нельзя — маршрут отвечает 400.

### Что показывает diff

`buildMigrationDiff()` собирает документ дважды — по прежнему и по целевому
профилю — и сравнивает результаты:

- **структура документа**: новые разделы, удалённые разделы, изменённая
  нумерация, число разделов, сохранивших номер;
- **снятые legacy-ссылки**: обозначения прежней редакции, которые встречались в
  документе и исчезают после миграции, с указанием замены
  (`ГОСТ 34.602-89 → ГОСТ 34.602-2020`);
- **новые и исчезнувшие требования** (по кодам);
- **конфликты**: замечания валидатора уровня `ERROR`;
- **нарушения структуры** относительно схемы целевого профиля;
- **неприменимые нормативы**: всё, что после миграции осталось в
  `NOT_APPLICABLE` или `UNKNOWN`;
- **блокирующие пробелы** проектного контекста.

Флаг `requiresAttention` означает: мигрировать можно, но документ ещё не готов к
согласованию.

## 3. Контрольные (golden) документы

`lib/gost34/__tests__/golden/` — девять типовых сценариев из плана:

```
generic-corporate-as     типовая корпоративная АС
ispdn                    обработка персональных данных
kii                      значимый объект КИИ
bank                     кредитная организация
nfo                      некредитная финансовая организация
air-gapped-as            изолированный контур
high-availability-as     повышенная доступность
simple-internal-system   простая внутренняя система
legacy-gost34-602-89     проект прежней редакции
```

Рядом с каждым сценарием лежит эталон `<id>.json` — слепок документа:
структура разделов с числом абзацев и подписями таблиц, коды требований,
статусы применимости по каждому нормативу, счётчики валидации, покрытие
трассировки, пробелы контекста и нарушения схемы.

Текст разделов в эталон намеренно не входит: иначе любая правка формулировки
переписывала бы все девять файлов и перестала бы читаться в ревью.

Если структура документа изменилась осознанно — эталоны обновляются:

```bash
npm run test:golden:update
```

Файлы эталонов исключены из Prettier (`.prettierignore`): их формат задаёт
генератор.
