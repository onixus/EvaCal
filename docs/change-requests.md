# Запросы на изменение требований (#103 §1, WP-2a/2b)

Запрос на изменение (ЗИ) фиксирует, **что** и **почему** меняется относительно
согласованной базы проекта, и собирает подтверждённую специалистом оценку
влияния. До решения по запросу действующая база (расчёт, его этапы, комплект
ГОСТ 34) не меняется.

## Что входит в этот этап

- Карточка запроса: номер `ЗИ-NN` (сквозной в проекте), название, инициатор,
  причина, исходная версия расчёта и (необязательно) комплект, выпущенный по
  этой версии.
- Затронутые требования выбираются из снимка базового комплекта и сохраняются
  снимком `{ id, code, text }` — последующие выпуски комплекта не меняют запрос.
- Предлагаемые изменения: суть + пункты «изменить / исключить» по затронутым
  требованиям и новые требования.
- Влияние (`lib/changeRequests/impact.ts`): связанные этапы базового расчёта
  строятся тем же движком, что и трассировка выпущенного комплекта
  (`buildTraceability`): ручные решения снимка (`manualLinks`, включая
  «намеренно не распределено») главнее, остальные требования связываются
  правилами (RULE, в UI помечены «по правилу»), legacy `mappedStageId` — только
  запасной вариант без ручного решения. Текст требования — действующая редакция
  (`getRequirementEffectiveText`). Также: документы комплекта к пересмотру,
  критерии приёмки затронутых требований как предварительный список проверок
  (формальные проверки — раздел 2 #103).
- Оценка специалиста: доп. часы, стоимость (Decimal, валюта базового расчёта,
  без НДС) и изменение срока в рабочих днях. **Все три значения вводятся
  явно.** Часы связанных этапов показываются только для справки и нигде не
  суммируются: связь требования с этапом не означает, что меняются все часы
  этапа. Значения со знаком — изменение может сокращать объём.
- История согласования: `ChangeRequestEvent`, только дополнение (UPDATE
  запрещён триггером), переоценка не стирает прежние значения — они остаются в
  `data` события.

## Жизненный цикл

```
draft ──submit──▶ submitted ──accept──▶ accepted   (новая версия расчёта/комплекта)
                     │  ▲     ──reject──▶ rejected
                     │  └─reopen── deferred ◀──defer──┘
```

- Править содержание и базу можно только в `draft`; правка передаёт
  `updatedAt` увиденной версии (оптимистическая блокировка, 409 при гонке).
- Передать на оценку (`submit`) можно только черновик; непустота проверяется в
  той же транзакции, что и переход.
- Оценку вносит/уточняет специалист только в `submitted`.
- Решения `accept` / `reject` / `defer` — из `submitted`, `reopen` — из
  `deferred`. Для `reject` и `defer` причина обязательна. Решение пишет
  `decidedBy/decidedAt` и событие журнала; `reopen` их очищает.
- `accepted` и `rejected` — конечные.

## Политика оценки

Оценка привязана к состоянию базы: при оценке сохраняется отпечаток
`estimateBaseHash` (`computeBaseFingerprint` в `lib/changeRequests/apply.ts`) —
SHA-256 от:

- этапов базового расчёта с параметрами Ганта (часы, роль, порядок,
  `parallel`, `approvalDays`, требования), явных зависимостей этапов
  (`StageDependency`), даты старта, рисков, часов РП и коммерческого профиля;
- содержательной части снимка базового комплекта (требования, связи,
  спецификация, переопределения разделов, проектный контекст и т. п.) и состава
  документов. Подписи, автор ТЗ, шаг мастера и `updatedAt` снимка не входят —
  они не меняют содержание.

Метки времени и статусы строк не входят. Отпечаток считается в транзакции под
той же блокировкой расчёта, что и перестроение этапов (`lockCalculationLedger`),
— при оценке и при принятии.

- **Принять** можно, только если база не менялась после оценки; иначе 409 и
  карточка показывает «нужна переоценка». Переоценка в `submitted` обновляет
  отпечаток.
- **Вернуть отложенный** (`reopen`): если база не менялась — оценка сохраняется,
  если менялась — сбрасывается целиком (специалист оценивает заново). Что
  произошло, записано в `data.estimate` события (`kept` / `cleared` / `none`).

## Принятие (одна транзакция)

1. Блокировка решений проекта и блокировка базового расчёта
   (`lockCalculationLedger`), повторная проверка статуса, оценки и отпечатка.
2. Цепочка: база запроса должна быть текущей головой (см. ниже); от одной
   версии принимается одно изменение, иначе 409.
3. `createCalculationVersion(parent = база)` — новая версия N+1 (этапы и риски
   клонированы).
4. В новую версию добавляется **отдельный риск `ИЗМ-NN`** с подтверждёнными
   часами; стоимость и срок указаны в описании. Часы связанных этапов не
   меняются и не суммируются.
5. Если у запроса есть базовый комплект — черновая версия комплекта по новой
   версии расчёта: снимок базы с правками требований (`modify` — новая исходная
   редакция и статус черновика, `remove` — требование и его связи удалены,
   `add` — требование `ИЗМ-NN.k`; у legacy-требований обновляется и
   заголовок), связи перенесены на этапы новой версии (сопоставление по
   порядку/названию/роли; несопоставленные отброшены). Подписи, автор ТЗ и шаг
   мастера из снимка базы не переносятся — черновик подписывают заново.
6. Строка листа внутренних изменений новой версии (источник
   `change_request`, ручной ввод этого источника запрещён).
7. `resultCalculationId` / `resultPackageId`, статус `accepted`, событие с
   версиями результата.
8. `Project.baselineCalculationId` фиксируется при первом принятом изменении
   (выигранная версия, а если сделка не выиграна — база запроса).

Любая ошибка откатывает всё; базовые расчёт, этапы и комплект не меняются ни
до, ни после принятия.

## Уведомления и очередь

- Подан на оценку / возвращён на оценку → пользователям с правом оценки
  (архитектор, админ): `cr_submitted`, `cr_reopened`.
- Оценён / принят / отклонён / отложен → автору запроса и инициатору, если
  инициатор — логин сотрудника: `cr_estimated`, `cr_accepted`, `cr_rejected`,
  `cr_deferred`. Запрос хранит логины, получатели находятся по `User.username`,
  неизвестные (обычно ФИО заказчика) пропускаются; себе о своём действии
  уведомление не приходит. Сбой уведомления не роняет действие (`notifySafe`).
- Уведомление ведёт на вкладку запросов проекта (`/projects/:id?tab=changes`).
- Очередь «Требует моего действия»: архитектору и админу — запросы на оценке
  («Оценить ЗИ-NN», после оценки — «Принять решение по ЗИ-NN»). Пункт очереди
  теперь есть и у пресейла — ради уведомлений о его запросах.
- Миграция `20261124100000_cr_notifications` расширяет CHECK вида и сущности
  уведомления и связывает виды `cr_*` с сущностью `change_request`.

## Проверки приёмки

Карточка запроса показывает проверки приёмки базового комплекта по
затронутым требованиям; пока запрос на оценке или принят, приёмка помечает их
«требует пересмотра» (`lib/acceptance/review.ts`, #124).

## Цепочка изменений и база

- Базовым комплектом может быть только выпущенный действующий комплект — не
  `draft` (черновик мастер перезаписывает при каждом сохранении) и не
  `archived` (заменён более новым выпуском).
- Голова цепочки — результат последнего принятого изменения, иначе
  первоначальная база (`baselineCalculationId`, до первого принятия —
  выигранная версия). Новый запрос можно создать, передать на оценку и принять
  только на голове (400/409 иначе). Пока база не определена (сделка не
  выиграна, изменений не было) — подходит любая версия проекта; первое
  принятие фиксирует базу.
- Сводка суммирует только изменения цепочки; принятые вне цепочки (например,
  исторические) показываются счётчиком и в итоги не входят.

## Первоначальный объём и изменения

Карточка проекта (строка в шапке) и «Коммерческая сводка» показывают
первоначальную базу (`baselineCalculationId`, до первого принятия —
`wonCalculationId`): часы, цену без НДС, плановое окончание — отдельно от суммы
принятых изменений (часы, стоимость, срок по подтверждённым оценкам) и итог
«база + изменения». Каждое изменение трассируется: `ЗИ-NN · vБаза → расчёт
vN → комплект vM` (`lib/changeRequests/totals.ts`, `summaryData.ts`).

Рядом с подтверждённой стоимостью показана цена версии-результата по ставкам
(вся версия без НДС) с пояснением: в версии изменение — строка `ИЗМ-NN` в
рисках, и её цена по ставкам ролей может отличаться от согласованной суммы;
итоги считаются по подтверждённой сумме.

## Защита базы и результата

Расчёт (и его комплекты), который является базой или результатом запроса на
оценке, отложенного или принятого, не удаляется: `DELETE /api/calculations/:id`
отвечает 409 с номерами запросов, а триггеры `Calculation_change_request_guard`
/ `GostPackage_change_request_guard` запрещают удаление на уровне СУБД (в том
числе каскадом). Отказ триггера (`restrict_violation`, гонка с подачей
запроса) API тоже переводит в 409.

Черновики и отклонённые запросы базу не держат: при удалении расчёта или
комплекта они удаляются вместе с ним (триггером). Черновик можно удалить и
явно — `DELETE /api/projects/:id/change-requests/:crId` (только `draft`, роли
ведения запросов); поданные запросы — история согласования и не удаляются.

## Номера версий

Номер версии расчёта и комплекта — max+1 в проекте. Создание версии
(`createCalculationVersion`, `createGostPackageVersion`, `releaseGostPackage`,
`saveGostPackageDraft`, `createDraftPackageVersion`) читает max и вставляет
строку в транзакции под advisory-блокировкой проекта (`lockVersionNumbers`),
поэтому параллельные создания не получают один номер. Уникального индекса
`(projectId, version)` нет: исторические данные его не гарантируют.

## Роли

| Действие                                 | Роли                      |
| ---------------------------------------- | ------------------------- |
| Просмотр, создание, правка, на оценку    | presale, architect, admin |
| Оценка часов / стоимости / срока         | architect, admin          |
| Принять / отклонить / отложить / вернуть | architect, admin          |

Совпадает с правами на сделку проекта (`/api/projects/[id]/deal`).

## API

- `GET /api/projects/:id/change-requests` — список и `headCalculationId`
  (допустимая база нового запроса); `?packageId=` — требования базового
  комплекта для выбора.
- `DELETE /api/projects/:id/change-requests/:crId` — удаление черновика.
- `POST /api/projects/:id/change-requests` — новый черновик.
- `GET /api/projects/:id/change-requests/:crId` — карточка с историей.
- `PATCH /api/projects/:id/change-requests/:crId` с `action`:
  `update` (черновик целиком), `submit`, `estimate`
  (`{ hours, cost, scheduleDays, comment? }`), `accept` | `reject` | `defer` |
  `reopen` (`{ comment }`, для reject/defer обязателен).

## Хранение

Таблицы `ChangeRequest` и `ChangeRequestEvent` (миграции
`20261026100000_change_requests`, `20261120100000_change_request_decisions` —
`estimateBaseHash`, `Project.baselineCalculationId`, CHECK результата,
триггеры защиты от удаления). Ссылки на проект, расчёт и комплект —
скалярные id без внешних ключей: запрос не каскадирует изменения в базу, общие
модели не меняются. При удалении проекта его запросы удаляются явно
(`DELETE /api/projects/:id`).

## Проверки

- `lib/changeRequests/*.test.ts` — влияние без автосуммы часов, переходы,
  валидация, маршруты: создание/правка/передача/оценка не пишут в расчёт,
  этапы и комплект.
- `lib/changeRequests/apply.test.ts`, `totals.test.ts`, `deleteGuard.test.ts` —
  правка снимка и перенос связей, отпечаток базы, итоги «база + изменения»,
  409 на удаление.
- `npm run test:change-requests:postgres` — живая PostgreSQL: база не меняется,
  CHECK-ограничения, уникальный номер при параллельном создании, append-only
  журнал, каскад; принятие создаёт трассируемую версию, сбой внутри принятия
  откатывает всё, политика переоценки, триггеры защиты.

## Ограничения

- `createCalculationVersion` переводит `approvalForStageId` и явные зависимости
  этапов (`StageDependency`, #118) на id клонов. Связи комплекта на этапы,
  которые не удалось сопоставить, не переносятся — движок трассировки их и так
  игнорирует.
- Принятие подтверждается диалогом с итогами изменения.
- Стоимость изменения — подтверждённая сумма запроса; цена новой версии по
  ставкам может отличаться (риск `ИЗМ-NN` тарифицируется как риск).
