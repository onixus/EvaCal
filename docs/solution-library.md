# Библиотека проектных решений

Часть #103, раздел 7 (WP-7a, пункты 7.1 и 7.2). Набор решения — версионируемый комплект «требования + работы + риски + проверки + фрагменты документов» с владельцем, областью применимости, источником и статусом утверждения. Применение наборов к проектам с сохранением происхождения (7.3) и предложения обновлений (7.4) — следующий шаг; содержимое уже спроектировано под них.

Экран: `/admin/solution-kits` (пункт меню «Библиотека решений» у архитектора и администратора).

## Модель

Миграция `20261118100000_solution_library`, перечисления — `TEXT + CHECK`.

`SolutionKit` — паспорт набора:

| Поле                   | Назначение                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------- |
| `key`                  | стабильный уникальный ключ (`^[a-z0-9][a-z0-9._-]{1,99}$`), не меняется            |
| `name`                 | название                                                                           |
| `ownerId`, `ownerName` | владелец (User.id без FK, имя снимком); `null` — системный набор                   |
| `scope`                | `{ industries: string[], productTypes: string[], notes: string }`                  |
| `source`               | происхождение: `preset:<id>`, `tor-template:<id>`, `manual`, …                     |
| `status`               | `draft` (нет утверждённой версии) → `approved` → `archived` (снят с использования) |

`SolutionKitVersion` — содержимое:

| Поле                             | Назначение                                           |
| -------------------------------- | ---------------------------------------------------- |
| `version`                        | номер, `@@unique(kitId, version)`                    |
| `status`                         | `draft` → `approved` → `archived`                    |
| `content`                        | JSON содержимого (схема ниже)                        |
| `changelog`                      | журнал изменений версии; обязателен со второй версии |
| `approvedBy/At`, `archivedBy/At` | подписи; CHECK требует их у утверждённой и архивной  |

Ограничения БД:

- `SolutionKitVersion_one_draft_key` — не больше одного черновика на набор (частичный уникальный индекс).
- Триггер `SolutionKitVersion_guard`: утверждённая версия неизменна; разрешён только переход `approved → archived` без правки содержимого, журнала и подписи утверждения; архивная версия не меняется вовсе; удалить можно только черновик. Следствие: набор с утверждёнными версиями нельзя удалить и каскадом — только архивировать.

**Удаление набора.** Маршрута удаления набора нет намеренно: на утверждённые версии будут ссылаться проекты (происхождение элементов), а триггер не даст удалить их и каскадом. Набор снимают с использования архивом (`PATCH … { status: 'archived' }`); набор только с черновиками при необходимости удаляет администратор БД вручную.

**Статус набора** пересчитывается: первое утверждение версии переводит набор в `approved`; архив последней утверждённой версии возвращает его в `draft` (применять нечего); архивный набор остаётся архивным, возврат из архива — в `approved` или `draft` по наличию утверждённых версий.

## Содержимое версии

Схема и проверка — `lib/solutionKits/content.ts` (`schemaVersion: 1`). Разделы:

| Раздел         | Элемент                                                                                    | Ссылки                                                            |
| -------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| `fields`       | поле опросника: `key`, `label`, `type`, `options`, `required`                              | —                                                                 |
| `requirements` | требование: `code`, `category`, `title`, `description`, `criterion`                        | —                                                                 |
| `stages`       | работа: `name`, `role`, `baseHours`, `hoursPerUnit`, `driver`, `notes`                     | `driver` → `fields` (числовое), `requirementIds` → `requirements` |
| `risks`        | риск: `description`, `hours`                                                               | `stageIds` → `stages`, `requirementIds` → `requirements`          |
| `checks`       | проверка: `criteria`, `method` (`INSPECTION`/`ANALYSIS`/`DEMONSTRATION`/`TEST` или `null`) | `requirementIds` → `requirements`, не пусто                       |
| `fragments`    | фрагмент документа: `sectionKey`, `title`, `text`                                          | `requirementIds` → `requirements`                                 |

Каждый элемент несёт `elementId` (`^[A-Za-z0-9][A-Za-z0-9._:-]{0,99}$`), уникальный во всей версии. Ссылки — только по `elementId` и только в указанный раздел. Новая версия копирует предыдущую вместе с `elementId`, поэтому элемент, применённый к проекту, получит происхождение `{ kitId, kitKey, kitVersion, elementId }` (`KitElementProvenance`) и будет сопоставим с любой версией набора.

Ограничения размера: содержимое версии — не больше 2 МБ в JSON, в одном списке ссылок (`requirementIds`, `stageIds`) — не больше 200, в разделе — не больше 2000 элементов (ошибки формы). Тело запроса к API — не больше 2,25 МБ: проверяется по Content-Length и по фактическому потоку до разбора JSON (413).

Проверка двухуровневая:

- **форма** (`parseKitContent`): типы, обязательные строки, часы `0…100000`, роли из `lib/roles.ts`. Ошибка формы не даёт сохранить черновик (400 с `issues`). Лишние ключи отбрасываются — хранится каноническая форма.
- **целостность** (`validateKitContent`): дубликаты `elementId` и ключей полей, висячие ссылки, ссылки не в тот раздел, повтор ссылки, нечисловой драйвер, поле-список (`select`) без вариантов, проверка без требований. Черновик с замечаниями сохраняется, но утвердить его нельзя (409 с `issues`).

## Сравнение версий

`lib/solutionKits/diff.ts`: элементы сопоставляются по `elementId` в пределах раздела — добавленные, удалённые, изменённые (список полей, значения до/после), число неизменных и флаг перестановки. Элемент, перенесённый в другой раздел, — удалён и добавлен. По умолчанию версия сравнивается с ближайшей предыдущей.

## Роли

| Действие                                                               | Кто                                              |
| ---------------------------------------------------------------------- | ------------------------------------------------ |
| читать библиотеку, создать набор (создатель — владелец)                | `architect`, `admin`                             |
| создать и править черновик                                             | `architect`, `admin`                             |
| удалить черновик                                                       | автор черновика, владелец-архитектор или `admin` |
| утвердить версию, архивировать версию, паспорт, архив набора, владелец | `admin` или владелец набора с ролью `architect`  |

У системного набора (`ownerId = null`) владельца нет — утверждает и архивирует только администратор. Владельцем можно назначить только архитектора или администратора; снять владельца — только администратор. Остальные экраны `/admin` по-прежнему только для администратора (группа маршрутов `app/admin/(core)`).

## API

| Метод и путь                                                 | Действие                                                                     |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `GET /api/solution-kits`                                     | список наборов (текущая утверждённая, черновик, число версий)                |
| `POST /api/solution-kits`                                    | `{ key, name, scope?, source?, content?, changelog? }` → набор и черновик v1 |
| `GET /api/solution-kits/:kitId`                              | паспорт и версии без содержимого                                             |
| `PATCH /api/solution-kits/:kitId`                            | `{ name?, scope?, source?, ownerId?, status?: 'archived' \| 'active' }`      |
| `POST /api/solution-kits/:kitId/versions`                    | новый черновик — копия последней версии                                      |
| `GET /api/solution-kits/:kitId/versions/:v`                  | содержимое, сводка по разделам, замечания целостности                        |
| `PATCH /api/solution-kits/:kitId/versions/:v`                | `{ content?, changelog? }` — только черновик                                 |
| `DELETE /api/solution-kits/:kitId/versions/:v`               | удалить черновик                                                             |
| `POST /api/solution-kits/:kitId/versions/:v/approve`         | `{ expectedUpdatedAt }` — утвердить черновик; изменён после просмотра — 409  |
| `POST /api/solution-kits/:kitId/versions/:v/archive`         | утверждённую версию — в архив                                                |
| `GET /api/solution-kits/:kitId/versions/:v/diff[?against=N]` | сравнение с предыдущей (или указанной) версией                               |
| `POST /api/solution-kits/validate`                           | `{ content }` → форма, целостность, сводка — без сохранения                  |

Утверждение несёт `expectedUpdatedAt` — `updatedAt` черновика, который видел утверждающий; условный `updateMany` по нему не даст утвердить черновик, поправленный после просмотра (409). Экран отправляет метку загруженной версии.

Действия пишутся в аудит (`solution_kit.*`).

## Встроенные наборы (сид)

`lib/solutionKits/builtin.ts` превращает статические пресеты `lib/presets/*` (ключ `preset.<id>`) и шаблоны ТЗ `lib/gost34/torTemplates/*` (ключ `tor.<id>`) в содержимое v1:

- пресет → поля опросника (`field-<key>`), этапы (`stage-01…`, драйвер — `elementId` поля, текст требований этапа — `notes`), риски (`risk-01…`); описание — в `scope.notes`;
- шаблон ТЗ → требования с исходными id, по проверке на каждый критерий приёмки (`chk-<id>`, метод не задан — его выбирает владелец), фрагменты «Область применения» и «Применимые стандарты».

`seedBuiltinSolutionKits()` (`lib/solutionKits/seed.ts`) вызывается из `prisma/seed.ts` (контейнер migrate выполняет сид при каждом старте). Сид идемпотентен: набор с существующим ключом не трогается, даже если пресет в коде изменился, — v1 могла уже применяться в проектах. Обновить встроенный набор — создать новую версию в библиотеке. Сид создаёт наборы системными (`ownerId = null`) и утверждёнными (`approvedBy = 'system'`). Пресеты и шаблоны ТЗ в коде не удаляются: опросники и мастер ТЗ пока работают с ними напрямую.

## Проверки

- `lib/solutionKits/content.test.ts` — форма, целостность, встроенные наборы валидны и детерминированы, дифф, правила ролей и переходов.
- `lib/solutionKits/routes.test.ts` — маршруты с хранилищем в памяти: допуск ролей, владелец, неизменность утверждённой версии, копирование в новую версию.
- `npm run test:solution-kits:postgres` (`scripts/verify-solution-kits.ts`, в цепочке Jenkins) — идемпотентный сид, триггер неизменности, CHECK и индекс одного черновика, новая версия не меняет старую.
