# Журнал факта и импорт трудозатрат

Часть #103, раздел 6 (WP-6a). Инфраструктура не привязана к конкретному трекеру: CSV и ручной ввод уже идут через журнал, коннектор к трекеру подключается реализацией `TrackerConnector` (`lib/integrations/tracker.ts`).

## Модель

| Таблица               | Назначение                                                                                                                                                                                                                             |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ActualEntry`         | Запись факта: расчёт, этап (может быть пустым — задача ещё не сопоставлена), источник, `externalId`, ключ задачи, автор, часы, даты, `externalUpdatedAt`, `syncedAt`, `deletedAt`. Уникальна по `(calculationId, source, externalId)`. |
| `ActualSyncRun`       | Прогон синхронизации: источник, режим (`incremental`/`full`), кто запустил, курсор, счётчики (создано/исправлено/без изменений/удалено/пропущено), ошибки (JSON).                                                                      |
| `ExternalTaskMapping` | Сопоставление ключа внешней задачи с этапом расчёта для источника.                                                                                                                                                                     |

`source` — `TEXT` с `CHECK`: `csv`, `manual` или идентификатор трекера (`[a-z][a-z0-9_-]*`, до 32 символов). Часы не отрицательны у всех источников, кроме `manual` (см. ручную поправку).

`Stage.actualHours`, `Stage.actualStartDate`, `Stage.actualEndDate` остаются в схеме и читаются всеми отчётами как раньше, но пишутся только пересчётом из журнала (`recomputeStageActuals`):

- часы — сумма неудалённых записей этапа с часами, не меньше нуля; нет таких записей — `null`;
- начало — ручная дата этапа, если задана, иначе самая ранняя дата записей источников (worklog показывает, что работа началась);
- окончание — **только ручная дата**: `actualEndDate` означает «этап завершён» (`lib/schedule.ts`), а дата последнего worklog этого не означает. Столбец `окончание`/`end` в CSV и `endedAt` трекера сохраняются в записи, но этап не закрывают.

Миграция `20261024100000_actuals_ledger` переносит уже внесённый факт: каждый этап с часами или датами факта получает одну запись `manual` с `externalId = stage:<id>`, поэтому итоги после миграции не меняются. Это базовая ручная запись: синхронизация источников её не трогает.

## Синхронизация источника

`syncLedgerSource` (`lib/actualsLedgerData.ts`) сравнивает записи источника по расчёту с пришедшими (`planSync`, `lib/actualsLedger.ts`) и в одной транзакции:

- **новый `externalId`** — создаёт запись;
- **тот же `externalId`, те же значения** — ничего не меняет (обновляет только `syncedAt`): повторный импорт не удваивает факт;
- **тот же `externalId`, другие значения** — исправление заменяет часы, даты, этап; ранее удалённая запись восстанавливается;
- **`externalUpdatedAt` старее сохранённого** — запись пропускается (устаревшая версия не затирает новую);
- **дубль `externalId` во входе** — берётся последний.

Внутри одного источника запись с тем же `externalId` **заменяется**. Записи разных источников **складываются**. С ручными часами (в том числе перенесёнными миграцией) импорт поступает по явному правилу — см. «Ручные часы при импорте».

Все записи журнала одного расчёта (синхронизация, ручная правка, сопоставление задач) выполняются под транзакционной блокировкой `pg_advisory_xact_lock`; если гонка всё же упирается в уникальный ключ (P2002), API отвечает 409 и операцию можно повторить.

**Политика пропавших записей.** Режим `full` означает, что источник отдал полный набор записей по расчёту: неудалённые записи источника, которых в нём нет, помечаются `deletedAt` (не стираются, выпадают из агрегата и восстанавливаются, если вернутся). Режим `incremental` (дельта с курсора, CSV по умолчанию) пропавшие записи не трогает. Коннектор трекера получает `full` только когда сам сообщает `complete: true`.

## Ручная правка

Ручной ввод — источник `manual`, две записи на этап:

- **базовая** `stage:<id>`: часы, введённые, когда других источников с часами у этапа нет (и перенесённые миграцией), плюс ручные даты начала и окончания. Синхронизация её не трогает, кроме правила «заменить ручные часы» при импорте (обнуляются только часы, даты остаются);
- **поправка** `adj:<id>`: если у этапа уже есть часы из источников, ввод итога записывается поправкой = введённое − (база + источники), с перечнем источников в `basis`. Итог этапа становится равен введённому, поправка может быть отрицательной.

Поправка сохраняется при инкрементальной синхронизации (новые worklog добавляются к итогу). Её снимает только **полная** синхронизация источника из `basis`, изменившая записи этого этапа: поправка подгоняла итог под прежние данные источника. Предварительный просмотр перечисляет такие этапы.

Пустое поле часов не трогает записи источников: если у этапа есть ручные часы, они убираются (база и поправка), иначе ввод считается «без изменений». Очистка даты возвращает начало по источникам; окончание без ручной даты пустое.

## CSV-импорт

`POST /api/calculations/:id/actuals/import`, тело JSON `{ csv, dryRun, mode, mappings, manualHours }` (или `text/plain` с `?dryRun=1&mode=full&manualHours=replace`). Сопоставления задач сохраняются в той же транзакции, что и записи журнала.

Форматы (разделитель `;` или `,`):

1. Старый позиционный: `этап;часы[;начало;окончание]`.
2. С заголовком — столбцы по именам: `id`, `задача`/`task`/`key`, `этап`/`stage`, `часы`/`hours`, `дата`/`date`, `начало`/`start`, `окончание`/`end`, `автор`/`author`. Подходит для выгрузки worklog из трекера.

**externalId строки CSV**: `id:<значение>`, если есть столбец `id`; иначе `h:` + SHA-256 от (ключ задачи, а без него — нормализованное имя этапа; дата, приведённая к `ГГГГ-ММ-ДД`, поэтому `02.03.2026` и `2026-03-02` совпадают; автор без учёта регистра). Явный `id` длиннее 190 символов заменяется хэшем (`idh:`). В старом формате нет даты и автора, поэтому ключом становится этап — повторный импорт исправляет значение этапа, как прежняя перезапись. Строки без `id` с одинаковым ключом в одном файле суммируются (одна запись источника); повторяющийся явный `id` — берётся последняя строка, превью об этом сообщает.

### Ручные часы при импорте

Строки бывают двух видов:

- **итог этапа** — без `id`, даты и автора (старый формат `этап;часы[;начало;окончание]`): «факт этапа = N». Старый импорт перезаписывал `Stage.actualHours`, поэтому перенесённая миграцией база такого этапа уже равна прежнему итогу;
- **worklog** — с `id`, датой или автором: «ещё N часов».

Параметр `manualHours` (выбор в панели, записывается в `ActualSyncRun.manualHours` и в аудит):

| Режим           | Что происходит с ручными часами этапов из файла                                                    |
| --------------- | -------------------------------------------------------------------------------------------------- |
| `auto` (умолч.) | этап со строками-итогами — `replace`, этап только с worklog — `add`                                |
| `replace`       | часы базовой записи обнуляются (ручные даты остаются), поправка снимается: итог этапа = данные CSV |
| `add`           | ручные часы остаются, данные CSV добавляются к ним                                                 |

Примеры: перенесённые 40 ч + повторный импорт `Анализ;40` = 40 ч, затем накопительный `Анализ;45` = 45 ч; перенесённые 120 ч + worklog 8 ч с датой = 128 ч; введённые вручную 40 ч + worklog 3 ч и 4 ч в режиме «заменить ручные часы» = 7 ч. Превью перечисляет все этапы файла с ручными часами (база и поправка) и правило, которое к ним применится.

**Сопоставление**: строка с задачей ищет этап по `ExternalTaskMapping` (источник `csv`), затем по имени этапа без учёта регистра и пробелов; этапы согласования факт не принимают, неоднозначные имена отклоняются. Несопоставленные задачи превью показывает списком с выбором этапа; выбранные сопоставления сохраняются при применении и используются в следующих импортах; уже записанные записи этой задачи (например, worklog трекера без этапа) переносятся на выбранный этап.

`dryRun` возвращает сопоставление и план (`counts`: новых, исправлено, без изменений, будет удалено) без записи. Применение пишет записи, прогон `ActualSyncRun` и аудит `actuals.import`.

Панель факта показывает источники записей у каждого этапа и сводку по источникам: число записей и часы по этапам, отдельно — записи без этапа (в итог не входят), время последнего обновления и итог последнего прогона.

## Коннектор к трекеру

`TrackerConnector.fetchWorklogs({ scope, cursor })` возвращает `worklogs` (id, ключ задачи, автор, часы, даты, `updatedAt`), `nextCursor` и `complete`. `runTrackerSync` превращает worklog в записи (`worklogsToEntries`; несопоставленные задачи сохраняются без этапа и не входят в агрегат; worklog с пустым или длиннее 200 символов id/ключом задачи отклоняется с ошибкой в `ActualSyncRun.errors`, остальные синхронизируются) и вызывает `syncLedgerSource`. Конкретный адаптер, хранение курсора и привязки расчёта к проекту трекера — следующий шаг после выбора трекера.
