## 1. Цель

Закрыть Horizon B как **продуктовый контур**, а не как набор API.

Реализованный результат: сотрудник видит и контролирует из UI:

1. Какой **проект** это (заказчик, статус, текущая смета).
2. Какая **версия расчёта** согласована.
3. Какой **комплект ГОСТ 34** ушёл заказчику.
4. Из каких **требований и решений мастера** он собран.
5. Возможность **скачать тот же ZIP** в любой момент (воспроизводимый SHA-256 checksum).

Демо-сценарий «Северный банк»:

> Архитектор открывает проект «Северный банк». Видит расчёт v2 (консервативный сценарий) и комплект ГОСТ v1 «на согласовании». Сравнивает покрытие с v0. Перевыпускает ТЗ — появляется v2, старый ZIP не перезаписывается. По share-ссылке заказчик скачивает _тот же_ файл и ставит approve. Сценарий автоматизирован в Playwright E2E (`e2e/severny-bank-release.spec.ts`).

Навигация по-прежнему «Все расчёты / Пресейл / Архитектор». Подписи в GET-экспорте — захардкоженные «Иванов / Петров».

## 3. Целевая модель

```text
Project
  ├── Calculation v1..N          (смета, сценарии, Гант)
  └── GostPackage v1..N          (нормативный выпуск)
        ├── snapshot             (требования, links, применимость, реквизиты, overrides)
        ├── artifact ZIP         (неизменяемый байтовый снимок)
        └── checksum SHA-256
```

Правила:

- Расчёт и комплект — версии **одного проекта**, не два острова.
- Генерация читает **снимок пакета**, а не «что сейчас в визарде».
- Утверждённый пакет иммутабелен: новый выпуск = новая версия.
- Документ — проекция снимка, не source of truth.
- Share-токен Horizon A расширяется правом `review` на пакет, без права менять смету.

---

## 4. Ключевые решения

1. **Не плодить `Requirement` как отдельную таблицу в первом проходе.** Снимок требований, связей и решений мастера кладётся в `GostPackage.snapshot` (JSON) рядом с уже существующим `metadata`. Отдельная нормализованная таблица — Horizon C, когда появятся поиск по требованиям и межпроектный реестр.
2. **Артефакт сначала на локальном volume**, не S3. Путь `gost-packages/<projectId>/<packageId>.zip` рядом с SQLite. Object storage остаётся C5.
3. **Checksum обязателен для статуса `approved`.** Для `draft` можно без ZIP. Переход в `under_review` / `approved` без артефакта и checksum — ошибка, не `console.error`.
4. **`recordRelease` больше не глотает сбои.** Если снимок/пакет не записался — экспорт 5xx. Иначе реестр врёт.
5. **Хаб расчёта остаётся**, но становится видом версии внутри проекта. Корень навигации — `/projects`.
6. **Diff первого прохода структурный**, без LLM: требования (добавлены/удалены/изменён текст), покрытие, разделы с override, профиль, состав документов.
7. **Не брать в этот горизонт:** Postgres, multi-tenant, очередь генерации, ПСИ/акт, новые пресеты, выравнивание android-app, LLM как автор ТЗ.

## 5. Изменения модели данных

Доработки `GostPackage` (Prisma / SQLite):

```text
snapshot        String?   // JSON: requirements v2, traceLinks, applicability,
                          // signatures, sectionOverrides, wizardStep, projectContext
artifactPath    String?   // относительный путь к ZIP на volume
checksum        String?   // SHA-256 ZIP; обязателен с under_review
releasedAt      DateTime?
releasedBy      String?
reviewComment   String?   // комментарий approve/reject
```

`status`: `draft | under_review | approved | rejected | archived` — без новых значений.

`Calculation` и `Project` не ломаем. `projectId` на расчёте уже есть; UI обязан его показывать и создавать.

Миграция: `prisma db push` / migrate. Старые пакеты без snapshot/artifact остаются `draft` «только метаданные»; повторный выпуск создаёт полноценную vN+1.

## 6. Этапы работ

### RR-1. Проект как первый экран — `[x] Выполнено`

- Пункт «Проекты» в `Nav`.
- `app/projects/page.tsx` — список проектов (заказчик, код, статус, число расчётов и пакетов, дата).
- `app/projects/[id]/page.tsx` — карточка проекта: текущий расчёт, лента версий расчётов, лента пакетов ГОСТ, коммерческий итог, покрытие трассируемости.
- Создание расчёта всегда садится в проект (`?projectId=`).
- Хаб `/calculations/[id]` содержит навигационную крошку «Проект → расчёт vN».

### RR-2. Снимок мастера в пакете — `[x] Выполнено`

- Wizard сохраняет/восстанавливает `GostPackage.snapshot` (файл `lib/gost34/snapshotPersistence.ts`).
- В снимок входят: требования v2 (`originalText` / `normalizedText` / source / status), manual trace-links и решения UNMAPPED, применимость, реквизиты, `sectionOverrides`, предложения ИИ `tzAuthor.proposals`, `wizardStep`.
- Повторное открытие мастера поднимает сохранённый снимок.
- `generateGost34Document` использует snapshot как приоритетный источник данных.

### RR-3. Неизменяемый ZIP и checksum — `[x] Выполнено`

- При выпуске формируется ZIP на диске + вычисляется SHA-256 в `checksum` (`lib/gost34/artifactStorage.ts`).
- Маршрут `GET /api/gost34/packages/:id/artifact` отдаёт сохранённый файл (staff или share `export`/`review`).
- Повторная выгрузка того же снимка детерминированно совпадает по checksum.
- Сбой записи пакета вызывает откат и возвращает HTTP 5xx.
- В карточке проекта: скачивание vN, статус, профиль, состав документов.

### RR-4. Согласование комплекта — `[x] Выполнено`

- Жизненный цикл: `draft → under_review (tw → gap) → approved | rejected`.
- Статус `approved` иммутабелен (повторная правка требует создания новой редакции vN+1).
- Share-scope `review`: чтение пакета + approve/reject + скачивание ZIP без права менять смету расчёта.
- Публичная страница ревью без служебного логина (`/review/:id`): состав, покрытие, замечания, комментарии.
- Логирование в `AuditEvent`: события `gost_package.submit`, `approve`, `reject`, `download`.
- Реквизиты и подписи извлекаются из снимка, а не из констант.

### RR-5. Структурный diff версий — `[x] Выполнено`

- Эндпоинт `GET /api/projects/:id/packages/diff?from=&to=`.
- Сравнение версий: добавленные/удалённые/изменённые требования, дельта покрытия трассируемости, изменённые разделы, смена профиля стандарта.

### RR-6. E2E «Северный банк» — `[x] Выполнено`

- Автоматизированный сквозной тест Playwright: `e2e/severny-bank-release.spec.ts`.
- Проверяет полный цикл: login → создание проекта → выбор отраслевого пресета → расчёт сметы → мастер ГОСТ 34 (сохранение черновика и восстановление) → выпуск ZIP → согласование по share-ссылке → проверка воспроизводимости checksum.

## 7. API (целевой контракт)

| Метод                                   | Назначение                                       | Доступ                            |
| --------------------------------------- | ------------------------------------------------ | --------------------------------- |
| `GET /api/projects`                     | список (уже есть)                                | staff                             |
| `GET /api/projects/:id`                 | карточка + версии (уже есть, расширить packages) | staff                             |
| `POST /api/projects/:id/packages`       | создать/обновить draft snapshot                  | staff                             |
| `POST /api/gost34/packages/:id/release` | собрать ZIP, checksum, `under_review`            | staff                             |
| `GET /api/gost34/packages/:id`          | метаданные + метрики снимка                      | staff или share `review`/`export` |
| `GET /api/gost34/packages/:id/artifact` | скачать сохранённый ZIP                          | staff или share `export`/`review` |
| `POST /api/gost34/packages/:id/review`  | `{ decision: approve\|reject, comment }`         | staff или share `review`          |
| `GET /api/projects/:id/packages/diff`   | структурный diff                                 | staff                             |

Существующий `GET/POST /api/calculations/:id/gost34` перестаёт быть единственной точкой выпуска: он либо делегирует в `release`, либо помечается deprecated после RR-3.

Расширение share: `scopes` += `review`. Токен без `write` не меняет calculation.

## 8. Тесты

Обязательные автотесты по этапам:

- **RR-1:** API-контракт списка/карточки проекта; крошка хаба.
- **RR-2:** round-trip snapshot (save → load → generate) в `lib/gost34` + repository.
- **RR-3:** checksum стабилен на фиксированном снимке; экспорт без успешного `recordRelease` — 5xx.
- **RR-4:** матрица ACL (staff / share review / share write / anonymous).
- **RR-5:** фикстура двух снимков → ожидаемый diff.
- **RR-6:** Playwright «Северный банк».

Golden-документы ГОСТ не ломаем: генератор по-прежнему проецирует модель; меняется только источник входа (snapshot vs live wizard).

## 9. Что сознательно не берём

| Идея                        | Почему позже                                                                                                                 |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Postgres + очередь + S3     | Нечего масштабировать, пока выпуск не воспроизводится                                                                        |
| Multi-tenant                | Сначала объект проекта, иначе tenant режет пустоту                                                                           |
| ПСИ / акт приёмки           | Новый шаблон на эфемерной модели снова станет «простынёй»                                                                    |
| Ещё пресеты / приказы ФСТЭК | Регуляторка без сохранённой применимости усиливает юрриск                                                                    |
| LLM как автор ТЗ            | Спроектировано отдельно: [LLM_TZ_AUTHOR_DESIGN.md](LLM_TZ_AUTHOR_DESIGN.md). Старт после RR-2 (снимок). Не в этом горизонте. |
| Выравнивание android-app    | Отдельный движок; не мешать контуру выпуска                                                                                  |
| Семантический diff ТЗ       | Horizon D5, после структурного diff                                                                                          |

## 10. KPI

- Повторный экспорт утверждённого пакета совпадает по checksum.
- Доля требований со статусом и источником ≥ 90% в демо «банк/КИИ».
- Вопрос «какая версия ушла заказчику» закрывается из карточки проекта.
- T_first_reopen: повторное открытие мастера без потери решений < 1 минуты.
- Ноль критичных находок ACL на новых package-роутах (checklist Horizon A).

## 11. Порядок внедрения

1. Влить текущие доработки хаба/сметы/матрицы, если они ещё не в `main` (PR #51 уже влит).
2. RR-1 → RR-2 → RR-3 — жёсткая цепочка: без проекта некуда вешать пакет, без снимка нечего хранить, без ZIP нечего согласовывать.
3. RR-4 и RR-5 после RR-3; RR-6 ведётся сразу, как появится выпуск.

Оценка суммарно: **4–6 недель** одного сильного full-stack с доменом.

После этого честно открываются Horizon C (Postgres, очередь) и D3 (полноценный customer portal).

## 12. Definition of Done

Горизонт закрыт, когда одновременно верно:

- [ ] В навбаре есть «Проекты»; карточка показывает расчёты и пакеты.
- [ ] Черновик мастера переживает перезагрузку.
- [ ] Утверждённый ZIP скачивается с диска, не генерируется заново.
- [ ] Повторная скачка = тот же SHA-256.
- [ ] Заказчик approve/reject по share-ссылке без staff-логина.
- [ ] Есть структурный diff двух пакетов.
- [ ] Playwright «Северный банк» зелёный в CI.
- [ ] `recordRelease` / release не глотает ошибки записи.
