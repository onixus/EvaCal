# Испытания и приёмка (#103, WP-4a)

Проверки приёмки связывают требование с конкретной утверждённой редакцией
комплекта ГОСТ 34 и фиксируют фактические результаты испытаний: кто проверял,
когда, что получилось, чем подтверждено.

WP-4a — проверки, результаты, замечания (модель, API, экран). WP-4b — решение
приёмочной комиссии, заполнение ПСИ и акта из фактов и пересмотр проверок по
запросам на изменение (раздел ниже).

## Модель

| Таблица                | Назначение                                                                                                                                                |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AcceptanceCheck`      | Проверка требования в редакции комплекта (`packageId`). Уникальна по `(packageId, requirementId)`. Код, заголовок, метод и критерии копируются из снимка. |
| `AcceptanceResult`     | Журнал результатов, только дописывается: `UPDATE` запрещён триггером `AcceptanceResult_no_update`.                                                        |
| `AcceptanceRemark`     | Замечание к проверке (при желании — к конкретному результату) с жизненным циклом; `createdById` — автор.                                                  |
| `AcceptanceRemarkEdit` | Журнал правок текста замечания: прежний и новый текст, кто и когда.                                                                                       |
| `AcceptanceEvidence`   | Вложение проверки: ключ в хранилище, имя, размер, SHA-256, загрузчик и время загрузки (фиксирует сервер); `resultId` — к какому результату прикреплено.   |

Перечисления хранятся как `TEXT` + `CHECK`. Дополнительно `CHECK` в БД:

- `passed`/`failed` требуют непустых `executorName`, `actualResult` и заданного `executedAt`;
- `verified` у замечания требует `verifiedBy`, `verifiedAt` и `retestResultId`;
- `resolved`/`verified` требуют `resolvedBy`, `resolvedAt`.

Миграция: `prisma/migrations/20261029100000_acceptance_checks`.

## Правила

- **Только утверждённая редакция.** Проверки заводятся и ведутся для комплекта
  со статусом `approved` (или `reviewStage = done`, кроме архивного).
  Выпущенный, но не утверждённый комплект ещё может измениться; черновик и
  архив редакцией не являются. Проверки привязаны к своей редакции навсегда:
  новая редакция получает собственные проверки, история старой не меняется.
- **Засев из снимка.** В проверку превращается требование снимка комплекта
  (`GostPackage.snapshot.requirements`) с критерием приёмки (`criterion` legacy
  или `acceptanceCriteria[]` v2) или методом проверки (`verificationMethod`).
  Требование без того и другого пропускается: придумывать критерий нельзя.
  Засев идемпотентен: добавляет только недостающие проверки.
- **Текущее состояние — последний результат.** Нет результатов — «не
  проводилась» (`not_run`). Состояние «пройдена» по умолчанию не назначается
  никогда.
- **Повторная проверка — новый результат.** Старые записи не меняются; история
  видна целиком (новые сверху). Явный сброс в `not_run` — тоже запись журнала.
- **Обязательные поля.** `passed`/`failed` — исполнитель, дата проведения (не в
  будущем) и фактический результат; `blocked` — причина блокировки.
- **Исполнитель и записавший различаются.** Исполнитель задаётся ровно одним
  способом: `executorSelf: true` — сам записывающий; `executorId` — пользователь
  системы, имя берётся из его учётной записи (свободный текст вместе с
  `executorId` отклоняется); `executorName` без `executorId` — ФИО лица вне
  системы (член комиссии, представитель Заказчика). `recordedBy` всегда
  проставляет сервер.
- **Форма не выбирает состояние за испытателя:** до явного выбора состояния
  кнопка записи недоступна.
- **Замечания:** `open → resolved → verified`; `resolved → open` (исправление
  не подтвердилось). `verified` — только со ссылкой на результат `passed` той же
  проверки, записанный после замечания. Проверенное замечание закрыто
  окончательно. Замечания не удаляются — это часть истории испытаний. Текст
  открытого замечания правит только автор или администратор; прежний текст
  сохраняется в `AcceptanceRemarkEdit` и в аудите (`previousText`/`newText`).

## Роли

| Кто                                   | Чтение | Засев, результаты, вложения, замечания |
| ------------------------------------- | :----: | :------------------------------------: |
| Архитектор, администратор             |   да   |                   да                   |
| ГАП                                   |   да   |                   да                   |
| Пресейл, тех.писатель, рецензент      |   да   |                  нет                   |
| Share-ссылка со scope `read` (и выше) |   да   |                  нет                   |

Отдельного share-scope для испытаний нет, поэтому share-ссылка только читает —
даже со scope `write`/`review`/`export`. Правило — `canRecordAcceptance` в
`lib/acceptance/rules.ts`.

## API

Все маршруты — под `/api/gost34/packages/[id]/checks`.

| Метод и путь                                     | Назначение                                                                                                                                        |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /checks`                                    | Проверки редакции с состоянием, историей, замечаниями и сводкой                                                                                   |
| `POST /checks`                                   | Засев из снимка (201 — добавлены, 200 — нечего добавлять, 422 — пусто)                                                                            |
| `POST /checks/[checkId]/evidence`                | Загрузка вложения (multipart `file`), возвращает вложение с `id`                                                                                  |
| `DELETE /checks/[checkId]/evidence?evidenceId=…` | Удаление неприкреплённого вложения (загрузчик или администратор)                                                                                  |
| `GET /checks/[checkId]/evidence?key=…`           | Скачивание вложения, прикреплённого к результату этой проверки                                                                                    |
| `POST /checks/[checkId]/results`                 | Новый результат: `status`, `executorSelf` / `executorId` / `executorName`, `executedAt`, `actualResult`, `evidenceIds[]`, необязательный `remark` |
| `GET /checks/[checkId]/remarks`                  | Замечания проверки                                                                                                                                |
| `POST /checks/[checkId]/remarks`                 | Новое замечание: `text`, необязательный `resultId`                                                                                                |
| `PATCH /checks/[checkId]/remarks/[remarkId]`     | `action`: `resolve` / `reopen` / `verify` (+ `retestResultId`) или `text`                                                                         |

Вложения: до 10 МБ, до 10 на результат; типы pdf, png, jpg/jpeg, txt, log, csv,
json, docx, xlsx, zip (расширение и MIME сверяются). Файлы лежат в хранилище
комплектов (`lib/gost34/storage.ts`, fs или S3) под ключом
`acceptance/<package>/<check>/<uuid>.<ext>`; ключ строит сервер. Размер
ограничивается до разбора multipart (по `Content-Length` и по фактическому
потоку). Имя очищается от пути и служебных символов. Загрузчика, время, размер
и SHA-256 фиксирует сервер при загрузке; результат ссылается на вложения только
по `id`, и прикрепить можно лишь неприкреплённые вложения этой проверки — один
раз. Прикреплённое вложение не удаляется.

**Очистка брошенных загрузок.** Вложение, загруженное, но так и не
прикреплённое к результату:

- удаляется сразу, если пользователь убрал его из формы (✕ → `DELETE`);
- иначе удаляется (строка и файл) при следующей загрузке к той же проверке,
  если ему больше суток (`ORPHAN_EVIDENCE_TTL_MS`, `cleanupOrphanEvidence`);
- не скачивается и в журнал испытаний не попадает.

Все изменения пишутся в журнал аудита (`acceptance_check.seed`,
`acceptance_result.record`, `acceptance_evidence.upload`, `acceptance_evidence.delete`,
`acceptance_remark.*`).

## Экран

Проект → «Реестр ГОСТ 34» → кнопка «Испытания» у редакции, для которой сервер
ведёт проверки (то же правило `isPackageEligibleForChecks`):
сводка по состояниям, формирование проверок из снимка, запись результата
(состояние, исполнитель, дата, фактический результат, вложения, замечание),
история результатов и жизненный цикл замечаний.

## Решение комиссии, ПСИ и акт из фактов (WP-4b)

### Модель

`AcceptanceDecision` (миграция `20261104100000_acceptance_decision`) — решение
приёмочной комиссии по редакции: `decision` (`accepted` |
`accepted_with_remarks` | `rejected`), `commission` (`[{ name, position?,
organization? }]`, не пусто), `basis` (обязательно), `exceptions` (`[{ checkId,
requirementCode, note }]`), `checksSnapshot` (по каким фактам принято:
проверка, состояние, id последнего результата), `decidedBy`/`decidedById`/
`decidedAt`. Решения только дописываются (`UPDATE` запрещён триггером);
`CHECK` в БД: «принять с замечаниями» — с непустым перечнем, «принять» — без
него.

### Правила решения (`lib/acceptance/decision.ts`)

- Решение принимается только по редакции, у которой есть проверки.
- «Принять» — только если каждая проверка пройдена, без открытых замечаний и
  без пометки «требует пересмотра».
- «Принять с замечаниями» — только с явным перечнем: каждая непройденная,
  заблокированная, непроведённая, с открытым замечанием или требующая
  пересмотра проверка должна быть в перечне с описанием; чистые проверки в
  перечень не входят.
- «Не принимать» — с основанием, без перечня.
- Действующее решение — последнее. Снимок фактов решения хранит по каждой
  проверке последний результат, число открытых замечаний и пометку
  пересмотра. Любое расхождение — новый результат, новое или закрытое
  замечание, поданный или снятый запрос на изменение, новая проверка — делает
  решение **устаревшим**: его выводы не печатаются, экран и диагностика просят
  решить заново. Решение «принять» устаревает и тогда, когда хотя бы одна
  проверка сейчас не пройдена или имеет замечание/пересмотр.
- Записывают решение те же роли, что и результаты (архитектор, ГАП, админ);
  share-ссылка только читает.

API: `GET /api/gost34/packages/[id]/decision` — действующее решение, признак
устаревания и история; `POST` — новое решение. `GET /checks` также отдаёт
`decision` и `needsReviewCount`.

### ПСИ и акт

Факты загружает сервер (`loadAcceptanceFacts`), клиент их не передаёт:
выгрузка и предпросмотр ПСИ, акта и комплекта (ZIP) берут последнюю
утверждённую редакцию расчёта с проверками или явно указанную
`acceptancePackageId` (должна относиться к расчёту и быть утверждённой, иначе
400). В снимке выпуска сохраняется `acceptance: { packageId, packageVersion,
decisionId }`.

- **ПСИ** (`psi34.ts`): таблица — из журнала проверок (фактический результат,
  исполнитель, дата, отметка); непроведённая проверка — «не проводилась».
  Удалены утверждения по умолчанию о контуре испытаний, отсутствии сбоев и
  полноте исходных данных — теперь это поля для комиссии; «испытания
  проводились по ПМИ» печатается только при хотя бы одном записанном
  результате; период испытаний — по датам результатов. Выводы — только из действующего решения, иначе пустые
  строки.
- **Акт** (`akt34.ts`): удалены «Система полностью соответствует требованиям
  ТЗ», «недостатков не выявлено», «считается принятой» и «работы выполнены в
  сроки», «работы, выполненные Разработчиком» и «Система включает комплект
  эксплуатационной документации» (объект приёмки и состав — нейтрально или
  полем для комиссии). Состав комиссии, результаты, замечания и заключение — только из
  решения; «не принимать» не печатает гарантийных обязательств.
- **Диагностика** (`diagnostics.gaps`, не блокирует выпуск):
  `acceptance.results` — нет фактов; `acceptance.notRun` — есть
  непроведённые проверки; `acceptance.decision` — нет решения или оно
  устарело; `acceptance.edition` — факты взяты из редакции старше последней
  утверждённой редакции расчёта.

### Пересмотр по запросам на изменение (§2.5)

Пометка вычисляется (`lib/acceptance/review.ts`), не хранится. Запрос на
изменение в состоянии «на оценке» или «принят», нацеленный на редакцию
(`basePackageId`) или, если комплект не указан, на её расчёт, помечает
проверки затронутых требований (`affectedRequirements` и
`proposedChanges.items[].requirementId`). Редакция, созданная по принятому
запросу (`resultPackageId`), им не помечается. Экран испытаний показывает
«Требует пересмотра: ЗИ-NN»; такая проверка не допускает решения «принять»
без перечня.
