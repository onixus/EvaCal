# Испытания и приёмка (#103, WP-4a)

Проверки приёмки связывают требование с конкретной утверждённой редакцией
комплекта ГОСТ 34 и фиксируют фактические результаты испытаний: кто проверял,
когда, что получилось, чем подтверждено.

Этот этап — модель данных, API и экран. Генераторы ПСИ и акта
(`lib/gost34/templates/psi34.ts`, `akt34.ts`) пока не читают записанные
результаты; заполнение ПСИ из факта — следующий PR.

## Модель

| Таблица            | Назначение                                                                                                                                                |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AcceptanceCheck`  | Проверка требования в редакции комплекта (`packageId`). Уникальна по `(packageId, requirementId)`. Код, заголовок, метод и критерии копируются из снимка. |
| `AcceptanceResult` | Журнал результатов, только дописывается: `UPDATE` запрещён триггером `AcceptanceResult_no_update`.                                                        |
| `AcceptanceRemark` | Замечание к проверке (при желании — к конкретному результату) с жизненным циклом.                                                                         |

Перечисления хранятся как `TEXT` + `CHECK`. Дополнительно `CHECK` в БД:

- `passed`/`failed` требуют непустых `executorName`, `actualResult` и заданного `executedAt`;
- `verified` у замечания требует `verifiedBy`, `verifiedAt` и `retestResultId`;
- `resolved`/`verified` требуют `resolvedBy`, `resolvedAt`.

Миграция: `prisma/migrations/20261029100000_acceptance_checks`.

## Правила

- **Только утверждённая редакция.** Проверки заводятся и ведутся для комплекта
  со статусом `approved` (или `reviewStage = done`, кроме архивного).
  Выпущенный, но не утверждённый комплект ещё может измениться; черновик и
  архив редакцией не являются. Проверки привязаны к своей редакции навсегда:
  новая редакция получает собственные проверки, история старой не меняется.
- **Засев из снимка.** В проверку превращается требование снимка комплекта
  (`GostPackage.snapshot.requirements`) с критерием приёмки (`criterion` legacy
  или `acceptanceCriteria[]` v2) или методом проверки (`verificationMethod`).
  Требование без того и другого пропускается: придумывать критерий нельзя.
  Засев идемпотентен: добавляет только недостающие проверки.
- **Текущее состояние — последний результат.** Нет результатов — «не
  проводилась» (`not_run`). Состояние «пройдена» по умолчанию не назначается
  никогда.
- **Повторная проверка — новый результат.** Старые записи не меняются; история
  видна целиком (новые сверху). Явный сброс в `not_run` — тоже запись журнала.
- **Обязательные поля.** `passed`/`failed` — исполнитель, дата проведения (не в
  будущем) и фактический результат; `blocked` — причина блокировки.
- **Исполнитель и записавший различаются.** `executorSelf: true` — исполнитель
  сам записывающий (`executorId` = его User.id); иначе `executorName` — ФИО
  члена комиссии или представителя Заказчика. `recordedBy` всегда проставляет
  сервер.
- **Замечания:** `open → resolved → verified`; `resolved → open` (исправление
  не подтвердилось). `verified` — только со ссылкой на результат `passed` той же
  проверки, записанный после замечания. Проверенное замечание закрыто
  окончательно. Замечания не удаляются — это часть истории испытаний; текст
  можно править, пока замечание открыто.

## Роли

| Кто                                   | Чтение | Засев, результаты, вложения, замечания |
| ------------------------------------- | :----: | :------------------------------------: |
| Архитектор, администратор             |   да   |                   да                   |
| ГАП                                   |   да   |                   да                   |
| Пресейл, тех.писатель, рецензент      |   да   |                  нет                   |
| Share-ссылка со scope `read` (и выше) |   да   |                  нет                   |

Отдельного share-scope для испытаний нет, поэтому share-ссылка только читает —
даже со scope `write`/`review`/`export`. Правило — `canRecordAcceptance` в
`lib/acceptance/rules.ts`.

## API

Все маршруты — под `/api/gost34/packages/[id]/checks`.

| Метод и путь                                 | Назначение                                                                                                                    |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `GET /checks`                                | Проверки редакции с состоянием, историей, замечаниями и сводкой                                                               |
| `POST /checks`                               | Засев из снимка (201 — добавлены, 200 — нечего добавлять, 422 — пусто)                                                        |
| `POST /checks/[checkId]/evidence`            | Загрузка вложения (multipart `file`), возвращает ссылку                                                                       |
| `GET /checks/[checkId]/evidence?key=…`       | Скачивание вложения, на которое ссылается результат этой проверки                                                             |
| `POST /checks/[checkId]/results`             | Новый результат: `status`, `executorSelf`/`executorName`, `executedAt`, `actualResult`, `evidence[]`, необязательный `remark` |
| `GET /checks/[checkId]/remarks`              | Замечания проверки                                                                                                            |
| `POST /checks/[checkId]/remarks`             | Новое замечание: `text`, необязательный `resultId`                                                                            |
| `PATCH /checks/[checkId]/remarks/[remarkId]` | `action`: `resolve` / `reopen` / `verify` (+ `retestResultId`) или `text`                                                     |

Вложения: до 10 МБ, до 10 на результат; типы pdf, png, jpg/jpeg, txt, log, csv,
json, docx, xlsx, zip (расширение и MIME сверяются). Файлы лежат в хранилище
комплектов (`lib/gost34/storage.ts`, fs или S3) под ключом
`acceptance/<package>/<check>/<uuid>.<ext>`; ключ строит сервер. При записи
результата сервер принимает только ключи этой проверки, проверяет наличие файла
и берёт размер и SHA-256 из самого файла, а не из запроса.

Все изменения пишутся в журнал аудита (`acceptance_check.seed`,
`acceptance_result.record`, `acceptance_evidence.upload`,
`acceptance_remark.*`).

## Экран

Проект → «Реестр ГОСТ 34» → кнопка «Испытания» у утверждённой редакции:
сводка по состояниям, формирование проверок из снимка, запись результата
(состояние, исполнитель, дата, фактический результат, вложения, замечание),
история результатов и жизненный цикл замечаний.
