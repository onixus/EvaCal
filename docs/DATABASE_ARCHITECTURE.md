# Архитектура данных EvaCal

Актуально: 29 сентября 2026 года.

## Контракт

PostgreSQL — единственная СУБД приложения, локальной разработки, тестов и production.
Docker/CI используют PostgreSQL 16. Наличие альтернативного хранилища артефактов
не означает альтернативную БД: S3/MinIO и файловый том содержат только ZIP/DOCX,
а связи, параметры, пользователи и состояние комплектов остаются в PostgreSQL.

```text
Browser → Nginx → Next.js routes / server components
                        ↓
                 lib/prisma.ts (lazy singleton)
                        ↓
                 PrismaPg / node-postgres → PostgreSQL
                        ↓
               metadata and artifact keys

Document storage → storage-data:/app/storage OR S3 bucket

prisma/schema.prisma → prisma generate → lib/generated/prisma
prisma/migrations    → prisma migrate deploy → PostgreSQL schema
```

Каноническая схема одна: `prisma/schema.prisma`, provider `postgresql`.
`prisma.config.ts` задаёт её путь и `prisma/migrations`; производных схем нет.
`PrismaPg` создаётся только при первом обращении и кэшируется во всех режимах,
включая production. Методы прокси привязаны к реальному клиенту: это сохраняет
идентичность интерактивных транзакций и не создаёт пул на каждое обращение.

## Конфигурация

`DATABASE_URL` обязателен. Принимаются `postgresql://` и `postgres://` с именем
базы и адресом сервера (либо Unix socket через параметр `host`). Параметры TLS,
кодированные пароли и схема сохраняются; `schema` также передаётся адаптеру.
Ошибка URL не раскрывает строку подключения и не включает резервный режим БД.
`containsInsensitive` всегда использует PostgreSQL `mode: 'insensitive'`.

В dev `.env.example` указывает на `localhost:5432`. В контейнере `localhost`
означает сам контейнер; для встроенного Compose-сервера оставьте `DATABASE_URL`
пустым, чтобы Compose собрал адрес `postgres:5432` из `POSTGRES_*`.
Установщик с `--database-url` подключает внешний сервер и не запускает встроенный.
Сборка использует фиктивный PostgreSQL URL только в команде генерации клиента;
runtime-образ не содержит URL подключения по умолчанию.

## Миграции и обновления

`npm run db:migrate -- --name NAME` создаёт миграцию на выделенной dev-базе;
учётной записи нужны права для shadow DB или отдельно настроенная shadow DB.
`npm run db:sync` применяет только закоммиченные миграции через `migrate deploy`.
`npm run db:status` показывает состояние истории. В production запрещено
использовать `migrate dev`, сброс базы или `db push` как замену миграции.

Существующие PostgreSQL-миграции перенесены в канонический каталог без изменения
имён и SQL; сохранены их checksums и совместимость с `_prisma_migrations`.
Новая миграция данных для этого рефакторинга не требуется. Не удаляйте старую
историю и не выполняйте baseline/reset существующей базы ради обновления пути.

В Docker последовательность: готовность PostgreSQL → migrate deploy → seed → app.
Миграции находятся в образе, а не в изменяемом томе. Обновление не меняет имя
Compose-проекта, пароль БД или имя тома `pg-data`. После ошибки миграции
автоматического отката схемы нет: нужна проверенная резервная копия и совместимая
версия приложения. Конфигурации других СУБД отклоняются до изменения установки;
данные из них переносятся отдельной контролируемой процедурой. Неиспользуемые
старые тома не удаляются автоматически.

## Резервное копирование

`evacal backup` останавливает своих писателей app/web, получает PostgreSQL custom
dump и локальные артефакты, сохраняет `.env` и возвращает ранее запущенные
контейнеры. Архив содержит секреты; права `600` не заменяют защищённое хранение.
Внешних писателей и S3 нужно включить в согласованную процедуру отдельно.

`restore` принимает архив PostgreSQL, проверяет пути и наличие дампа до остановки
сервисов и использует `pg_restore --single-transaction --exit-on-error`.
Текущие параметры подключения не перезаписываются архивной `.env`.
Не копируйте файлы работающего `pg-data` вместо PostgreSQL-aware backup.
Подробности и ограничения: [инструкция эксплуатации](../deploy/README.md).

## Проверки

`npm run test` проверяет URL, ленивый клиент, поиск, единственную схему/адаптер и
checksums опубликованной истории. `npm run test:deploy` проверяет установщик,
сохранность секретов, режимы встроенной/внешней БД, архивы и Compose-конфигурации
(для последних нужен Docker Compose CLI).

`npm run test:postgres` выполняет реальные CRUD, поиск без учёта регистра для
кириллицы, каскадное удаление по внешнему ключу и rollback интерактивной транзакции.
Запускайте на выделенной тестовой PostgreSQL-базе после `npm run db:sync`.
Проверочные записи откатываются, миграции команда проверки не применяет.
Jenkins поднимает одноразовый PostgreSQL через `scripts/ci-postgres.sh`;
ручной workflow CI использует сервис PostgreSQL. Автоматические GitHub Actions
не включаются этим изменением. Перед публикацией образы проходят
`scripts/smoke-docker.sh`: миграции, повторный запуск, non-root, артефакты, HTTP/TLS.
