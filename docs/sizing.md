# Сайзинг как отдельная версионируемая оценка (#101, раздел 5)

Сайзинг описывает **техническую потребность** (CPU/RAM/диски, EPS, поток, сессии, узлы,
лицензионные единицы), а не закупаемые SKU. Позиции спецификации остаются закупаемыми
строками; связь со сайзингом лишь указывает, какую метрику покрывает строка.

## Модель данных

Миграция `prisma/migrations/20261108100000_sizing` (TEXT + CHECK вместо enum):

| Модель                 | Назначение                                                                                                                                                                                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `SizingProfile`        | Профиль (ключ, название, домен, архив).                                                                                                                                                                                                                                        |
| `SizingProfileVersion` | Версия правил: `rules` (JSON), `assumptions`, `source`, статус `draft → approved → archived`, автор/утвердивший. `@@unique(profileId, version)`. **Утвержденная версия неизменяема** — триггер `SizingProfileVersion_immutable` (разрешен только переход approved → archived). |
| `SizingRun`            | Прогон расчета: закрепленная версия профиля (или `source = manual`), входы, сценарии, рассчитанные `outputs`. **Только добавление** — триггер `SizingRun_append_only`; удаление — только каскадом с расчетом.                                                                  |

Миграция засевает утвержденные v1-профили `siem`, `idm`, `ngfw` из `lib/sizing/builtin.ts`
(совпадение JSON проверяет `lib/sizing/builtin.test.ts`).

## Правила профиля

```jsonc
{
  "inputs": [
    { "key": "ngfw_clusters_count", "label": "...", "type": "number", "default": 1, "min": 0 },
  ],
  "derived": [{ "key": "headroom_factor", "formula": "1 + capacity_headroom_percent / 100" }],
  "outputs": [
    {
      "key": "nodes",
      "label": "Узлы",
      "kind": "nodes",
      "unit": "шт.",
      "formula": "ngfw_clusters_count * (ngfw_ha_required ? 2 : 1)",
      "round": "ceil",
    },
  ],
  "scenarios": [
    { "key": "no_ha", "label": "Без резервирования", "overrides": { "ngfw_ha_required": "false" } },
  ],
  "tables": {
    "tier": {
      "rows": [
        { "upTo": 10, "value": 1 },
        { "upTo": null, "value": 5 },
      ],
    },
  },
}
```

- Имена из прототипа объекта (`constructor`, `prototype` и т. п.) и имена функций зарезервированы;
  входы, таблицы и значения ищутся только по собственным ключам. Разобранные формулы кэшируются.
  Бесконечность/NaN (переполнение) дает «неизвестно» с предупреждением.
- Количество позиции считается точно: `ceil(requiredQuantity / unitCapacity)` в BigInt-десятичной
  арифметике `totals.ts`; результат вне диапазона спецификации — «невозможно проверить».
- Формулы — безопасный язык (`lib/sizing/expression.ts`, без `eval`): числа, `true/false`,
  `+ - * / %`, сравнения, `&& || !`, `?:`, функции `max min ceil floor round abs if lookup`.
- Формула видит только объявленные выше имена: циклы невозможны, ссылки проверяются при
  сохранении версии.
- **Отсутствие ≠ 0** (семантика #111): вход без ответа и без `default` неизвестен, зависящая
  метрика = `null` («невозможно рассчитать») с перечнем недостающих входов. `default` — это
  допущение профиля: оно применяется только при отсутствии ответа и попадает в список допущений
  метрики. Значение вне `min/max` ограничивается с предупреждением.
- Сценарии (`ha`, `no_ha`, `growth`, `retention_x2` …) переопределяют входы формулами от входов
  базового сценария; базовый сценарий `base` всегда рассчитывается.

## Прогоны

- Прогон по профилю сохраняется только для **утвержденной** версии и хранит результаты, поэтому
  новая версия профиля не меняет старые прогоны.
- Ручной сайзинг — тоже прогон (`source = manual`), метрики вводит пользователь, основание
  обязательно.
- Гость (share-токен, анонимный пресейл) получает версии профиля без формул, производных величин,
  таблиц и переопределений сценариев — только входы и названия метрик.
- Ответы вида «10 000» (пробел, неразрывный или узкий неразрывный пробел между группами по три
  цифры) читаются как 10000 (`lib/presets/answerValues.ts`, общий разбор с пресейлом).
- Предпросмотр без сохранения доступен по любой утвержденной версии; по черновику — архитектору и
  администратору (чтобы увидеть влияние нового профиля до утверждения).

## Связь со спецификацией и влияние

Строка спецификации получает необязательное поле
`sizingRef { runId, metric, scenario?, requiredQuantity, unitCapacity? }`
(старые снимки без него валидны). При сохранении редакции сервер проверяет, что прогон принадлежит
расчету и `requiredQuantity` совпадает с сохраненным результатом; снимок получает `sizingRunIds`.

Предпросмотр влияния (`lib/sizing/impact.ts`) сравнивает новый прогон (новая версия профиля или
новые входы) с потребностью, зафиксированной в редакции:

- `coverage = quantity × unitCapacity`, баланс `coverage − newRequired` → дефицит / избыток /
  покрыто; предлагаемое количество `ceil(newRequired / unitCapacity)`;
- разница стоимости — точная десятичная арифметика `lib/specification/totals.ts`, итоги до/после по
  валютам;
- компонент комплекта (`includedIn`) проверяется по покрытию и количеству, но собственной стоимости
  не имеет (правило 3a `totals.ts`): суммы строки и разница стоимости — `null`, итоги несет строка
  комплекта;
- нет метрики, метрика не рассчитана или у позиции нет количества → **«невозможно проверить
  соответствие»**, а не успех; такие строки не применяются;
- строки без связи не меняются; строка, чье количество отличается от расчетного по связанному
  прогону, считается ручным решением и меняется только с явным `allowManualOverride`;
- применение создает **новую черновую редакцию** обычным путем `saveSpecification` (проверка
  версии, 409 при устаревшей редакции); измененные строки требуют повторного подтверждения.

## API

| Метод и путь                                              | Доступ                                                                                                                                     |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/sizing/profiles`                                | любой вошедший сотрудник (черновики — только admin/architect)                                                                              |
| `POST /api/sizing/profiles`                               | admin, architect                                                                                                                           |
| `POST /api/sizing/profiles/:id/versions`, `PATCH` (архив) | admin, architect                                                                                                                           |
| `GET/PATCH/POST /api/sizing/versions/:versionId`          | правка черновика, `{action: approve, expectedHash}` (хэш просмотренного содержимого, иначе 409) или `{action: archive}` — admin, architect |
| `GET /api/calculations/:id/sizing`                        | как чтение спецификации (share `read`)                                                                                                     |
| `POST /api/calculations/:id/sizing`                       | запись (share `write`): прогон по профилю или `{source: 'manual'}`                                                                         |
| `POST /api/calculations/:id/sizing/impact`                | чтение; `{runId}` или `{profileVersionId, inputs}`                                                                                         |
| `POST /api/calculations/:id/sizing/apply`                 | запись; `{runId, version, selections[]}` → новая черновая редакция                                                                         |
| `POST /api/calculations/:id/sizing/link`                  | запись; связать строку с метрикой или снять связь (`runId: null`)                                                                          |

## UI

Вкладка «Сайзинг» в карточке расчета (`components/SizingPanel.tsx`): выбор профиля (по ключам
опросника), входы, предзаполненные из ответов и редактируемые отдельно, предпросмотр влияния,
прогоны со сценариями, связь метрики с позицией, ручной сайзинг, новая версия профиля для
архитектора. Панель спецификации показывает связи строк с сайзингом.

## Пресейл-preview

`lib/presets/implementationSizing.ts` (ТЗ/ПМИ и метрики пресейл-preview) не изменен: он
по-прежнему строит тексты требований и пресейл-метрики из ответов. Засеянные v1-профили
воспроизводят его формулы (тест `engine.test.ts` сверяет метрики при полностью заданных ответах);
расхождение только в отсутствующих ответах — профиль возвращает «неизвестно», пресейл помечает
значение как «не задано». Перевод пресейл-preview на профили — отдельный шаг.

## Проверка

- `npx vitest run lib/sizing` — язык формул, HA вкл/выкл, 0 против отсутствия, сценарии,
  совпадение с пресейлом, влияние, маршруты и права доступа.
- `npm run test:sizing:postgres` — неизменяемость утвержденной версии (триггер), закрепление
  версии прогоном, новая версия не меняет старые прогоны, предпросмотр по черновику,
  применение создает черновую редакцию, ручное количество не перетирается.
