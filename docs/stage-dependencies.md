# Зависимости этапов, ближайшая дата старта и сравнение вариантов

Часть #103, раздел 5 «Ресурсное планирование», пункты 5.2 и 5.4 (WP-5e).
Продолжение `docs/work-calendars.md` (5.1). Пункт 5.3 (конкретные специалисты и

## Модель

| Модель            | Назначение                                                                                                                                                                     |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `StageDependency` | Расчёт, этап-предшественник, зависимый этап, тип (`FS`, TEXT + CHECK — место для SS/FF), пауза `lagDays` (0…365 рабочих дней). Пара уникальна, петля запрещена CHECK, каскады. |
| `PlanScenario`    | Сохранённое сравнение вариантов: название, автор, варианты и сводка результата (JSON). Никогда не применяется автоматически.                                                   |

Миграция `20261027100000_stage_dependencies`. Циклы длиннее одного ребра
отсекает API (`validateDependencies` в `lib/scheduling.ts`).

## Расчёт Ганта

Без явных зависимостей Гант строится прежним алгоритмом без изменений
(неявная цепочка «после всех предыдущих», `parallel` — вместе с последним
непараллельным этапом, согласование — сразу после своего этапа). Это проверено
сравнением с графовым алгоритмом на 200 случайных планах.

С зависимостями (`scheduleItems(items, start, config, dependencies)`):

- этап с явными зависимостями стартует не раньше завершения каждого
  предшественника **вместе с его согласованием заказчиком** плюс `lagDays`
  целых рабочих дней по производственному календарю; неявная цепочка и флаг
  `parallel` для него не действуют;
- остальные этапы — по неявным правилам (в том числе ждут зависимый этап, если
  он выше по списку);
- расчёт идёт в топологическом порядке (Кан). Явная зависимость «назад» по
  списку замыкается на неявную цепочку — это цикл, API отвечает 409;
- пауза: день, на который пришёлся конец предшественника (если не в самом
  начале окна), паузой не считается; старт — начало первого рабочего дня после
  паузы. Праздник внутри паузы её удлиняет.

## Перестройка этапов на месте

`rebuildStages` (правка списка этапов, даты старта, пересчёт по анкете) больше
не удаляет и не создаёт все строки заново. Прежние строки Stage сопоставляются с
новым планом (`matchStageRows`): по `id` прежней строки (редактор этапов его
передаёт), иначе по названию и роли с предпочтением той же позиции; строка
согласования — та, что шла сразу за своим основным этапом. Совпавшие строки
обновляются (только плановые поля), новые создаются, удаляются только убранные
этапы. Всё — одной транзакцией под блокировкой журнала факта
(`lockCalculationLedger`).

Поэтому факт этапа, записи журнала факта (`ActualEntry`), сопоставления задач
трекера (`ExternalTaskMapping`) и явные зависимости переживают правку этапов.
Агрегат факта сохранённых этапов не пересчитывается: их записи не меняются.
У **удалённого** этапа записи журнала остаются с `stageId = null` (FK
`SetNull`, журнал это поддерживает — часы видны как несопоставленные и могут
быть сопоставлены заново), сопоставления задач этого этапа удаляются каскадом.
Выбран этот вариант, а не отказ 409: удаление этапа — штатная правка оценки,
а факт при этом не теряется. Зависимость, у которой пропал этап или которая
после перестановки смотрит «назад», снимается.

Своя длительность согласования теперь хранится и на основном этапе (раньше —
только на строке согласования, а редактор читал основной этап и при повторном
сохранении сбрасывал её к 3 дням). Для строк, сохранённых раньше, она берётся со
строки согласования (`primaryInputsFromStageRows`).

## Ближайшая доступная дата старта

`GET /api/calculations/:id/earliest-start?from=YYYY-MM-DD&days=182&drafts=1`
перебирает рабочие дни календаря расчёта начиная с `from`, на каждую дату
строит Гант заново (с зависимостями) и проверяет, что часы расчёта по ролям и
неделям помещаются в ёмкость (`capacityFor`: календарь, резервы) поверх
взвешенного спроса остальных проектов (без других версий того же проекта).
Роль без заданной ёмкости не ограничивает. Ответ: дата старта и конца,
`shiftDays` относительно текущего старта, первая мешающая роль/неделя на дату
`from`. Ничего не пишет; кнопка «Перенести старт» вызывает `/api/capacity/apply`.

## Сравнение вариантов

`POST /api/capacity/what-if` с `variants: [{ id, label, changes: [...] }]`
(до 5 вариантов, до 10 изменений в каждом):

- `{ type: 'shift', calculationId, shiftDays }` — перенос старта; Гант
  перестраивается по календарю и зависимостям;
- `{ type: 'contractor', calculationId, role, share, ratePerHour? }` — доля часов
  роли уходит подрядчику (вне ёмкости); со ставкой — разница стоимости против
  ставки роли расчёта;
- `{ type: 'team', role, headcountDelta, from, to, hoursPerWeek?, costPerHour? }` —
  временное изменение ёмкости роли (масштабируется календарём, как резерв); со
  стоимостью часа — затраты.

Ответ — базовый план и каждый вариант: конец затронутых расчётов и сдвиг в днях,
недели перегруза (всего и по ролям), пик загрузки, разница стоимости, часы
подрядчика, матрица (кнопка «На карте»). Прежний формат `shifts` возвращает
матрицу, тоже с перестройкой Ганта по календарю.

**Варианты ничего не пишут.** Применить можно только перенос старта и только
через `POST /api/capacity/apply`, который теперь перестраивает Гант на месте по
календарю шаблона и зависимостям (id этапов и внесённый факт сохраняются).
Поэтому конец расчёта в варианте совпадает с тем, что получится после
применения. Подрядчик и изменение команды оформляются отдельно (ёмкость — в
админке). `POST /api/capacity/scenarios` сохраняет сравнение (сводку без матриц)
для истории, `GET` — последние 20.

## Интерфейс

- Карточка расчёта архитектора: в Ганте зависимый этап помечен «↳» с подсказкой
  о предшественниках; под Гантом — подбор ближайшей даты старта; отдельная
  карточка «Зависимости этапов» — редактор (предшественник → этап, пауза).
- `/capacity`: блок «Сравнение вариантов» — добавить сдвиг, подрядчика или
  изменение команды, сравнить, показать вариант на тепловой карте, применить
  сдвиг, сохранить сравнение.

## Права

Чтение (зависимости, ближайшая дата, сохранённые сравнения) — планирующие роли,
как у ресурсного плана. Запись зависимостей, what-if, apply, сохранение
сравнения — `architect` и `admin`. Зависимости утверждённого расчёта не
меняются (409), как и его этапы; перенос старта через apply разрешён, как и раньше.

## Ограничения

- Только тип FS. SS/FF потребуют расширить CHECK и `buildConstraints`.
- Зависимости только внутри одного расчёта (между проектами — нет).
- Подбор даты смотрит роли, а не конкретных специалистов (это 5.3).
- Утверждённые расчёты не перестраиваются при правке календаря сами — только
  при переносе старта через apply.
